# Analyzer: ревизия проверки семантики

Срез `09472ab`. Штатный повторный прогон — **152/152**. Дополнительные сценарии ниже прошли через parser, сбор контекста и разрешение типов, затем `SemanticAnalyzer.analyzeWithResult`. Для отмеченных случаев выполнен также `TACCompilerImpl.compile` с TemplateInstantiator. [Код анализатора](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt) · [Помощники существующих тестов](../analyzer/src/test/kotlin/org/nnezh/SemanticAnalyzerTestSupport.kt)

## Ошибка пользователя превращается в исключение Kotlin

```bred
fun f(): Int { return [] }
```

Анализ завершился **NullPointerException**. Второй пример `fun f() { val x: Boolean = [] == [] }` тоже бросает NPE. Пустой `ArrayInitializationExpressionASTNode` не записывает тип в таблицу, однако return использует `scope.get(expression)!!`, бинарная операция — такие же предположения об обоих операндах. Ошибка обнаружена в analyzer до TAC. G-52 описывает отсутствие типа пустого массива, эти случаи показывают последствия вне объявления массива.

**Проверка исправления.** Публичный метод возвращает Left с предметной диагностикой, когда ожидаемый тип не допускает initializer или его тип не удаётся вывести. Контроль — `val a: Int[0] = []` сохраняет оговорённое поведение. У непустого initializer таблица хранит тип элемента: это специальная форма инициализации, которую нельзя безоговорочно использовать как полноценное значение массива. [Обработка ArrayInitialization, Return и BinaryExpression](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt)

## Некорректные объявления принимаются

| Вход | Фактический результат | Следующий шаг |
|---|---|---|
| `fun f(x: Int, x: Long): Long { return x }` | Right, чтение x имеет Long. Полный путь до TAC тоже успешен. | До `Scope.put` проверить уникальность параметров, показать оба объявления. Контроль — разные имена и одинаковые типы допустимы. |
| `fun f() { val a: Int[1] = [1] val a: Int[1] = [2] }` | Right без предупреждений, полный путь тоже успешен. | Объявление массива должно пользоваться правилом повторных имён текущего блока. |
| `fun f() { val a: Int = 1 val a: Int[1] = [2] }` | Right без предупреждений. | Проверить пересечение scalar/array в обе стороны. У scalar-ветки проверка повторного объявления уже есть. |
| `type P(x: Int) type P(y: Long) fun f() {}` | Right и успешный TAC. | Диагностика в общем сборщике объявлений до analysis. [Разбор parser](PARSER_REVIEW.md) |
| `instance Missing<Int> { fun hello(): Int { return 1 } } fun f() {}` | Right, в том числе через полный путь до TAC. | G-47. Проверять наличие typeclass, совпадение обязательных методов и сигнатур независимо от использования instance. |

`Scope.put` просто присваивает запись; проверка уникальности выполняется вызывающими ветками неравномерно. Общая операция объявления переменной должна различать ошибку в текущей области, затенение родительской области и допустимое новое имя. Это позволит массивам и параметрам пользоваться тем же контрактом. [Scope и объявления](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt)

## Проверка потока управления зависит от конструкции

```bred
fun f() {
    for (i in 0 to 3) {
        return println("a")
        println("dead")
    }
}
```

Этот пример получил Right без предупреждений и успешно дошёл до TAC. Замена for на `while (true)` дала `BLOCK_CONTAINS_CODE_AFTER_RETURN`. `ForStatementAstNode` посещается с `checkControlFlow=false`, флаг наследуется вложенными областями. Отключение защищает от синтетического инкремента после return, но охватывает также пользовательские инструкции внутри тела.

**Исправление.** Проверять исходное тело цикла до добавления инкремента либо явно различать происхождение инструкций. Тестировать unreachable внутри одного for, вложенного if в for и контрольного while. Текущее описание семантики говорит об отключении для синтетического блока; фактическое распространение флага шире. [ForParser](../parser/src/main/kotlin/org/nnezh/bred/ast/ForParser.kt) · [Флаг областей и BlockFlow](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt) · [Документация](semantic_analysis_draft.md)

**Полный when с return во всех ветках отклоняется.** Для `type S = A | B` и `fun f(s: S): Int { when (s) { A -> { return 1 } B -> { return 2 } } }` получено `EXPLICIT_RETURN_IS_EXPECTED`. Анализатор проверяет полноту when, но `statementGuaranteesReturn` учитывает только return и if с else. Документация описывает именно этот текущий предел. Это отдельное расширение анализа потока, оно возможно при statement-when и не требует when со значением. Контроль — убрать одну возвращающую ветку и сохранить ошибку. [Return guarantees](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt)

## Где анализ теряет сведения и где его границы

- **Предупреждения могут исчезать по пути вверх.** По чтению кода: BinaryExpression собирает warnings детей, но возвращает пустой список; handleFunctionCallExpression при успехе тоже возвращает пустой; Unary и While отбрасывают предупреждения операнда или условия. Сейчас многие выражения дают только ошибки, но when может анализировать блоки. Это риск контракта накопления. Для регрессии выбрать поддерживаемый expression с дочерним предупреждением и проверить весь путь результата.
- **Флаг вызова меняется в AST.** `isConstructorCalling` записывается анализатором, тогда как выбранная сигнатура функции, привязка переменной и вариант образца не возвращаются. Тип `Int` сам по себе не различает два разных n. Это источник повторных семантических решений downstream. [Последствия в TAC](TAC_REVIEW.md)
- **Допустимость операции для языка и для backend расходится.** Сравнение двух String принимается TypeValidator, а C backend печатает запрещённое сравнение структур. Время жизни возвращаемого локального массива тоже не проверяется. Граница ответственности требует отдельного правила; подробности и нативные проверки уже описаны. [Backend](C_BACKEND_REVIEW.md)
- **Глобальные инициализаторы проверяются до регистрации пользовательских функций.** G-50. Сначала решить допустимость такого вызова, затем согласовать порядок регистрации и реализацию глобального хранения G-79.

**Первой задачей я бы выбрала проверку повторного объявления массива.** Есть готовый соседний образец scalar-ветки и три маленьких случая для контроля. Следом — диагностический результат для пустого initializer и устранение различия for/while.
