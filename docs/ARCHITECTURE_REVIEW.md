# Архитектурный разбор Bred

Срез `09472ab`, 12 ноября 2026. Это отдельный список предложений по устройству компилятора. Для каждого указаны наблюдение в исходниках, цена текущего решения и одна проверяемая граница изменения. Примеры ниже — сценарии для будущих тестов. Основание разбора — чтение кода и результаты [предыдущей ревизии](AUDIT.md). Приоритеты исправления дефектов остаются в [TODO](TODO.md).

## Что стоит сохранить

Разделение на frontend, TAC и C backend уже помогает локализовать ошибки. Например, для `Just(value)` в снимке видно чтение тега и извлечение поля. Если оба присутствуют, причину неверного результата можно искать дальше по цепочке. C backend зависит только от `common` и способен принимать TAC напрямую. Это ценная граница для быстрых тестов без парсера и MSVC. [Снимок 3AC](https://github.com/nnezhevskii/bred/blob/09472ab043c817532dc8ca729cd12c86b923d483/tac/src/test/resources/deploymentHealthRadar.3ac) · [Зависимости backend](../c-backend/build.gradle.kts)

### 1. Дать специализации шаблонов и анализатору одно правило для типа оператора

`TemplateInstantiator.inferType` для бинарного выражения возвращает тип левой части. `TypeValidator.produceBinaryType` учитывает оба операнда и сам оператор. Поэтому на выражении `1 < 2` специализатор получает `Int`, а анализатор — `Boolean`. Это существенно для `id(1 < 2)`, где объявлена `fun id<T>(x: T): T { return x }`: тип аргумента выбирает тело конкретной специализации ещё до основного анализа.

**Первый шаг.** Вынести вычисление результата уже типизированных операндов в чистую функцию, доступную обеим стадиям. Правило может жить рядом с моделью операторов в `parser`, от которого уже зависит `analyzer`. Диагностику и поиск типов операндов оставить вызывающей стадии. Импорт `TypeValidator` из `analyzer` в `parser` создал бы цикл Gradle-зависимостей.

**Готово, когда** вызов `id(1 < 2)` создаёт специализацию для `Boolean`, `id(1 + 2)` — для `Int`, а недопустимая операция в аргументе получает диагностику. Объём первого изменения ограничен бинарными операторами. [Вывод типа в шаблоне](../parser/src/main/kotlin/org/nnezh/bred/codegenerator/TemplateInstantiator.kt) · [Правила анализатора](../analyzer/src/main/java/org/nnezh/TypeValidator.kt)

### 2. Сохранить идентичность объявления после выхода из области видимости

`SemanticAnalysisResult` передаёт дальше тип каждого выражения. Для двух локальных `n: Int` этих данных недостаточно: при чтении нужно знать, какое объявление нашёл анализатор. В TAC имя снова берётся из лексемы. C backend объединяет локальные объявления с одинаковыми именем и типом на всю функцию. Сходная проблема у служебных имён: для `for (i in ...)` парсер создаёт обычный идентификатор `_right_borderi`.

```bred
fun main() {
    val n: Int = 1
    if (true) {
        val n: Int = 2
        printInt(n)
    }
    printInt(n)
}
```

**Первый шаг.** Для локальных скаляров создавать при объявлении идентификатор привязки и сохранять его для каждого чтения и записи. Передавать эти данные в TAC вместе с существующей таблицей типов. Ключи нынешней таблицы сравниваются по идентичности AST-узлов, поэтому TAC должен получать именно проанализированный экземпляр дерева. Исходное имя сохранить для сообщений и читаемого 3AC.

**Готово, когда** пример печатает 2 и 1, а в TAC видны две разные ячейки. Вторым изменением можно провести через ту же границу выбранную сигнатуру перегрузки. Для неё нужен идентификатор функции, для синтетической границы цикла — отдельная привязка. Это три самостоятельных изменения. [Семантический результат и Scope](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt) · [Генератор TAC](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt) · [Разворачивание for](../parser/src/main/kotlin/org/nnezh/bred/ast/ForParser.kt)

### 3. Собрать общий проход от ProgramRoot до TAC

`BredToCCompiler.compileChecked` и `TACCompilerImpl.compile` оба собирают контекст, разрешают типы, специализируют шаблоны, снова собирают контекст и разрешают типы, запускают анализ и строят TAC. При этом входы действительно различаются: root API читает файлы и объединяет программу со stdlib, а TAC API принимает строку для изолированных примеров. Раздвоен именно порядок обработки уже собранного дерева.

**Первый шаг.** Выделить в `tac` один проход, принимающий `ProgramRoot` и способ создать контекст с нужными extern. Возвращать TAC либо ошибку с указанием стадии. Оба API адаптируют результат к своим существующим контрактам: root возвращает `Either` и генерирует C, TAC API выдаёт инструкции и сохраняет привычный для тестов способ сообщить об ошибке. Повторные разрешения типов пока нужны для появившихся специализаций.

**Готово, когда** порядок фаз описан одной исполняемой функцией, root по-прежнему подставляет stdlib и поддерживает переданные extern, а снимки TAC по-прежнему работают с самостоятельным исходником. Проверить успешную generic-программу, ошибку неизвестного типа и ошибку чтения stdlib. [Root API](../src/main/kotlin/org/nnezh/BredCompilationFactory.kt) · [TAC API](../tac/src/main/kotlin/org/nnezh/compiler/TACCompiler.kt)

### 4. Уточнить, что именно хранит реестр объявлений

`ProgramGlobalContext.functions` хранит одно `FunctionMeta` на имя, а `addFunction` присваивает значение по этому ключу. При двух перегрузках последняя запись заменяет первую. Семантическая область видимости умеет искать по типам аргументов, а `TemplateInstantiator.inferType` при разборе обычного вызова обращается к записи по имени. В результате потребители одного объявления получают разные наборы кандидатов.

**Первый шаг.** Хранить список кандидатов по исходному имени и ввести запрос выбора по сигнатуре. Проверить `id(pick(1))` для `pick(Int): Int` и `pick(Long): Long` в двух порядках объявления. Владение реестром можно уточнить локально: сборщик регистрирует объявления, стадии-потребители запрашивают кандидатов, специализатор явно добавляет сгенерированные объявления.

**Отдельное решение для типов.** `ProgramContextCollector.handleTypes` предварительно регистрирует имена, затем дважды обновляет продукты через `repeat(2)`. Прежде чем менять это место, проверить цепочку из четырёх продуктов в прямом и обратном порядке, а также цикл. Если результат зависит от порядка, отделить объявление имени от окончательного определения полей и сформулировать правило для циклов по G-73. Само наличие двух проходов ещё не доказывает ошибку. [Сбор объявлений](../parser/src/main/kotlin/org/nnezh/bred/context/ProgramContextCollector.kt) · [Реестр](../parser/src/main/kotlin/org/nnezh/bred/context/ProgramGlobalContext.kt) · [Потребитель метаданных](../parser/src/main/kotlin/org/nnezh/bred/codegenerator/TemplateInstantiator.kt)

### 5. Передавать проверенный образец ветки when в генератор

Парсер сохраняет `Just(value)` как выражение вызова, а `else` — как отсутствие условия. По типу субъекта анализатор различает образец суммы и обычное выражение, находит вариант, проверяет число полей и имена привязок. В `LLTACGenerator.buildWhenStatement` снова вызывается собственный `sumBranchPattern`. Каждое расширение образцов требует синхронно поддержать две трактовки одного синтаксиса.

**Первый шаг.** Добавить в результат анализа для ветки суммы выбранный вариант и проверенные привязки полей. Генератор берёт из результата тег и поля, затем выпускает существующие сравнения и переходы. Оставить парсеру общую форму условия: одинаковая синтаксическая запись может иметь разный смысл в зависимости от типа субъекта.

**Готово, когда** `Just(value)`, вариант без данных, `else` и обычная ветка сравнения дают прежний TAC, а неизвестный вариант и повторное имя всё ещё отклоняются анализатором. Это можно сделать при нынешнем statement-`when`, независимо от решения про возвращаемое значение G-71. [Парсер](../parser/src/main/kotlin/org/nnezh/bred/ast/WhenParser.kt) · [Проверка образцов](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt) · [Понижение в TAC](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt)

### 6. Сделать вызов в TAC самодостаточной операцией

У `CALL` записано число аргументов. Их значения C backend читает из предыдущих инструкций по отрицательным смещениям, с приведением типов. Затем по имени вызова и типу результата определяет, обычная это функция, конструктор продукта или вариант суммы. Связь «какие значения передаются» зависит от положения инструкций в списке.

**Первый шаг.** Для обычного вызова сформировать объект вызова с целью, упорядоченными операндами и необязательным результатом. Вычислять выражения аргументов в прежнем порядке. `PrettyPrinter` может печатать привычные `PARAM` и `CALL` из этого объекта, чтобы снимки оставались удобными для чтения. При переходе учесть backend-тесты, которые конструируют инструкции напрямую. Затем можно передавать явный вид конструктора.

**Готово, когда** для `f(g(x), h(y))` обе внутренние функции вычисляются однократно в исходном порядке, а backend получает оба операнда внешнего вызова без просмотра соседних инструкций. Дополнительно проверить вызов без аргументов и `Unit`-результат. ### 7. Зафиксировать интерфейс Bred ↔ C для extern

В `ExternalFunctionSpecs` есть имя Bred, аргументы и результат. Этого достаточно для проверки типов. Для компоновки нужно также знать, какой C-символ реализует данную сигнатуру. Обе формы `doubleToString` имеют одно имя, а в runtime реализована форма с одним аргументом. Изменение только списка сигнатур позволяет принять программу, которая сломается при нативной сборке.

**Первый шаг.** Для одной функции проследить путь от extern-сигнатуры до вызова и C-реализации. Указать имя C-символа там, где оно отличается от Bred. Для старой буферной перегрузки сначала решить, входит ли она в поддерживаемый интерфейс. Если входит, ей потребуется отдельная реализация или адаптер.

**Готово, когда** маленькая Bred-программа вызывает поддерживаемую форму, компилируется и линкуется вместе с `runtime.c`, а неподдерживаемая сигнатура получает диагностику frontend. Сравнения только имён недостаточно, поскольку здесь различаются аргументы и тип результата. ### 8. Разделить результат сборки, сообщения для человека и владение файлами

`CCompilerInvocationResult` уже хранит код завершения MSVC отдельно от сообщений. Наружу `CExecutableBuilder.build` возвращает список строк, а `Main` пытается восстановить успех по словам в тексте. Одновременно builder управляет временным C-файлом с путём, вычисленным из имени exe. Так в одном месте сходятся две независимые обязанности: сообщить результат и освободить только файлы своей сборки.

**Первый шаг.** Закрыть G-75 проверкой сохранности заранее созданного файла при раннем выходе и при обычной сборке. Затем сохранить структурированный результат до CLI, включая сбой до запуска компилятора. Если публичный метод со списком сообщений нужен существующим клиентам, его можно оставить адаптером. В сообщениях допустим любой путь, в том числе каталог `errors`.

**Как проверять границы.** С подставным `CCompilerInvoker` дёшево проверить ошибку, успешный код и владение файлами. На машине с MSVC держать отдельный небольшой сквозной тест, который запускает exe и сравнивает вывод. Пример из пункта 2 годится для такой проверки: совпадение текста C само по себе не проверяет значение внешней переменной после блока. [Builder](../src/main/kotlin/org/nnezh/CExecutableBuilder.kt) · [CLI](../src/main/kotlin/org/nnezh/Main.kt) · [Текущие корневые тесты](../src/test/kotlin/org/nnezh/root/BredCompilationFactoryTest.kt)
