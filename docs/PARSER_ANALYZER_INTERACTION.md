# Как parser и analyzer работают вместе

Срез `09472ab`. Самая существенная зависимость здесь — порядок разрешения имён, специализации и проверки типов. Parser хранит синтаксис, но модуль parser также владеет семантической подготовкой. Поэтому одной пары «построить AST → вызвать SemanticAnalyzer» для полной программы с шаблонами недостаточно.

## Фактический путь

```text
Lexer → parser → ProgramRoot с TypeRef
    → собрать имена типов и объявления
    → разрешить TypeRef
    → заново собрать контекст
    → специализировать generic и instance
    → собрать контекст появившихся объявлений
    → снова разрешить типы
    → SemanticAnalyzer
    → то же дерево + expressionTypes + warnings
    → TAC
```

Корневой компилятор до сбора контекста объединяет stdlib с пользовательским ProgramRoot. TACCompiler принимает самостоятельный исходник. Анализаторские тесты имеют два помощника: с инстанцированием и без. Все три пути повторяют часть одной последовательности. [Root](../src/main/kotlin/org/nnezh/BredCompilationFactory.kt) · [TACCompiler](../tac/src/main/kotlin/org/nnezh/compiler/TACCompiler.kt) · [TestSupport](../analyzer/src/test/kotlin/org/nnezh/SemanticAnalyzerTestSupport.kt)

## Где модули уже расходятся

| Решение на ранней стадии | Ожидание следующей | Проверенный эффект |
|---|---|---|
| Parser разворачивает for с обычным строковым именем | Analyzer видит корректные lexical scopes и отключает flow для synthetic content | Пользовательское имя захвачено, unreachable в теле for пропущен. |
| Parser принимает [] как Expression | Analyzer ожидает тип после успешного visit | `return []` даёт NPE. |
| Parser сохраняет параметры списком | Analyzer кладёт каждый по имени в Map | Второй x заменяет первый без ошибки. |
| Collector регистрирует тип по имени | Analyzer проверяет функции и globals, а declarations доверяет | Два P и instance неизвестного class проходят полный путь. |
| Специализатор определяет бинарный тип по левой части | Analyzer использует оператор и оба типа | `id(1 < 2)` получает специализацию Int, затем отклоняется на Boolean. |
| Analyzer возвращает тип, но не выбранную привязку | TAC повторяет поиск по имени | Ссылка на параметр Off может превратиться в конструктор Flag. [Пример](TAC_REVIEW.md) |

## Что именно гарантировать на границах

1. **После синтаксиса** доступны исходные литералы без сужения, места объявлений и исходное тело каждой управляющей конструкции. Некорректный разделитель даёт ASTError. Неизвестное имя типа остаётся TypeRef до resolver.
2. **После регистрации объявлений** каждое имя либо соответствует определённому набору кандидатов, либо есть диагностика повтора. Все виды объявлений проверяются независимо от того, использованы ли они. Отложенная специализация тела generic может оставаться отдельным правилом, но её границу нужно описать.
3. **При специализации** тип аргумента подчиняется тем же правилам операторов, что и при основном анализе. Для выбора instance нужны проверенные типы аргументов и явный набор кандидатов. Это устраняет конкретное расхождение, не требует запускать весь SemanticAnalyzer из parser.
4. **После анализа** успех означает, что следующая стадия получает необходимые факты для всех допустимых исполняемых выражений, а недопустимый initializer уже дал диагностику. Таблицы связаны с точной версией дерева. Warnings сохраняются при подъёме из дочерних узлов.
5. **При понижении** синтетические переменные получают свои идентичности, проверенные исходные имена сохраняют выбранные привязки. Завершение функции согласовано с анализом путей. У when проверка полноты и return во всех ветках должны использовать совместимые сведения.

## Кто должен владеть изменением

Повтор параметра и local array удобнее закрыть общей операцией analyzer для объявления привязки. Повтор type/typeclass/instance — стадией регистрации глобальных объявлений. For сохранить в parser, проверить его исходное тело в analyzer и развернуть перед TAC. Диапазон Int проверить там, где выбирается IntLiteral; исходную величину до проверки сохранить. Все эти задачи опираются на уже воспроизведённые примеры и могут делаться отдельно.

Для устранения дрейфа общего pipeline можно выделить проход от собранного ProgramRoot до результата анализа. Файловая загрузка stdlib останется у корня, тест самостоятельного фрагмента сможет явно выбрать свою среду. В результате изменение порядка фаз переносится в одно место. Потребители должны сохранять прежний контракт ошибок, чтобы рефакторинг не заставил менять смысл текущих тестов.

## Пять проверок стыка

| Сценарий | Проверяемое свойство |
|---|---|
| Параметр `_right_borderi` и for с i | Пользовательская ссылка разрешена к параметру, служебная граница имеет другую идентичность. |
| `return []` | Left с диагностикой, без исключения Kotlin. |
| Два параметра x | Ошибка повтора до перезаписи, в сообщении доступны места обоих параметров. |
| `id(1 < 2)` | Специализация для Boolean согласована с типом аргумента, полный путь до TAC успешен. |
| Полный when с return в каждой ветке | Выбранный контракт завершения проверяется на уровне analyzer и сохраняется в TAC; удаление return из одной ветки меняет результат проверки. |

Для одной короткой сессии достаточно второго сценария. Для понимания архитектуры лучше первый: в нём одновременно видны исходный синтаксис, преобразование дерева, область видимости и данные, которые нужно передать в TAC.
