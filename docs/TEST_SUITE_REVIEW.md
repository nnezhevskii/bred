# Тесты Bred — что они проверяют и как их перестроить

Срез ветки `phoenix`, коммит `26b9618`. Основание — настройки Gradle, исходники тестов и JUnit XML полного прогона на JDK 25 с MSVC. Выполнено 489 проверок, прошли 474, упали 15, пропущено 0. Это число запусков, включая параметризованные и динамические случаи. Общего отчёта о покрытии строк и ветвей по всем модулям в изученном дереве нет. Kover подключён в корневом проекте. Из числа тестов нельзя вывести процент покрытия языка.

## Карта активного набора

У каждого модуля основной каталог — `<модуль>/src/test/kotlin`. В таблице модуль указывает на последнюю проверяемую стадию. Тест, который начинает с текста Bred, может пройти несколько предыдущих стадий.

| Где | Выполнено / упало | Вход, результат и смысл проверки |
|---|---:|---|
| lexer | 48 / 0 | 43 случая `LexerTest` проверяют токены и лексические ошибки. Ещё 5 у `SourceReaderTest` проверяют чтение файлов, отсутствующий путь, каталог, расширение, пример в репозитории |
| parser | 105 / 2 | 83 у `ParserTest`, 12 у `RootParserMigrationTest`, 10 у `ProgramGlobalContextTest`. Здесь вместе находятся проверки формы AST по исходнику, отдельные обходы дерева и тесты контекста типов |
| analyzer | 156 / 4 | 129 у `SemanticAnalyzerTest`, 20 миграционных, 7 у форматтера. Сильное место — положительные и отрицательные пары для областей видимости, массивов, сумм и payload. Помощники запускают lexer, parser и resolver. Для специализации есть отдельный путь |
| tac | 140 / 5 | 45 у `LLTAGCompileExpectationsTest`, 83 у `TACInstructionSequenceTest`, 12 у `TACTestingFrameworkTest`. В первых двух Bred компилируется до инструкций. В третьем проверяется способность самих матчеров отличать верный IR от испорченного |
| c-backend | 17 / 0 | `CTranspileTest` подаёт вручную составленный TAC и сравнивает полученный C или ошибку трансляции. Покрыты прототипы, массивы, конкатенация, варианты сумм, повторное использование объекта. MSVC в этих 17 проверках не вызывается |
| корень | 23 / 4 | 13 проверок файлового Bred → C API, 3 проверки сборщика с настоящими временными файлами и подставным вызовом компилятора, 6 нативных сценариев для полей и чисел, 1 тест JVM CLI отдельным процессом. Все активные наборы встроены в обычные задачи `test`. Команда `.\gradlew.bat :test` выбирает только корень, `.\gradlew.bat :tac:test` — модуль TAC, а `.\gradlew.bat test --continue` из корня запускает набор задач по проекту. Нативные тесты используют `assumeTrue` по наличию `vcvars64.bat`. При сравнении прогонов на разных машинах проверять также число пропусков. ## Откуда берётся путаница

1. **В корне видны два поколения тестов.** Корневая сборка включает только `org/nnezh/root/**/*.kt`. В `src/test/kotlin/org/nnezh/ast` лежат 16 Kotlin-файлов с 412 строками-аннотациями `@Test`, в соседнем `semantic` — 3 файла с 232. Все 19 файлов вне активного source set. Старые тесты импортируют прежние пакеты и классы AST. Эти 644 аннотации не входят ни в 489 запусков, ни в графу skipped. 12 parser- и 20 analyzer-проверок с названием Migration переносят отдельные сценарии, иногда по несколько утверждений в методе. Равенство покрытия при переносе пока не установлено. [Фильтр Gradle](../build.gradle.kts) · [Parser migration](../parser/src/test/kotlin/org/nnezh/bred/ast/RootParserMigrationTest.kt) · [Analyzer migration](../analyzer/src/test/kotlin/org/nnezh/RootSemanticMigrationTest.kt)
2. **Длинная цепочка вызовов создаёт иллюзию сквозной проверки.** Для семантики перегрузок прямой анализатор может принять программу, которую публичный компилятор отвергнет на специализации. На другом конце цепочки 17/17 зелёных тестов рендерера совместимы с тем, что строковая копия в exe печатает имя переменной. Каждый уровень отвечает на свой вопрос. В имени или расположении теста полезно показывать, где заканчивается его наблюдение. [Семантические помощники](../analyzer/src/test/kotlin/org/nnezh/SemanticAnalyzerTestSupport.kt) · [C backend](../c-backend/src/test/kotlin/org/nnezh/compiler/CTranspileTest.kt)
3. **Один вход учитывается много раз.** В TAC есть 22 стабильные программы в `src/test/resources`. Фабрика JUnit создаёт динамические проверки отдельных функций и объявлений. Поэтому 83 результата одной серии включают более мелкие проверки, а 12 тестов матчеров защищают тестовую инфраструктуру. При этом четыре проверки радара в parser, analyzer и корне закомментированы. JUnit их вообще не обнаруживает. [Фабрика тестов](../tac/src/test/kotlin/org/nnezh/lltag/TACInstructionSequenceTest.kt) · [Исходник радара](../tac/src/test/resources/deploymentHealthRadar.bred)

## Что объединить, разделить и убрать

| Место | Предлагаемое изменение | Что сохранить |
|---|---|---|
| `ParserTest`, `SemanticAnalyzerTest` и оба `Root*MigrationTest` | При работе над конкретной темой собрать тесты по правилам языка. Первые кандидаты — приоритет операторов и повтор сигнатуры функции. Сверить вход, путь подготовки и утверждения, объединить совпадения, оставить дополнительные граничные случаи. Большой analyzer-класс удобно разделить на области видимости, управление потоком, типы и вызовы | Проверки кода ошибки, места и предупреждений. Анализ до и после специализации должен оставаться явно различимым |
| Старые корневые `ast` и `semantic` | Для одной темы за раз сопоставить старые случаи с активными. Перенести уникальные отрицательные примеры на текущий API. После сверки убрать старую группу из дерева тестов или архивировать с пометкой о версии | Смысл утверждения. Простое включение папок в Gradle вернёт зависимости от старого AST. Более важны отличающиеся сценарии, чем число перенесённых методов |
| Две серии ожиданий TAC | Контракты операндов, типов и привязок из текстовых проверок переносить на существующие типизированные матчеры. Тесты самого листинга собрать у `PrettyPrinter`. Например, для глобального `Long[2]` проверить объявление, значения и ссылку из `LOAD`. Для `Array<Int>` и `Array<Long>` отдельно проверить различимость текста | Точный порядок оставить там, где он наблюдаем, например порядок двух вызовов с побочными эффектами. Положительные и отрицательные тесты матчеров полезны, особенно подмена массива с тем же именем |
| `user function calls use mangled target name` | Сейчас метод получает `val tac` и завершается без утверждения. Подмена цели вызова оставит его зелёным, пока компиляция завершается. Сравнить цель `CALL` с объявленной функцией в IR. Если другой тест уже проверяет именно эту связь, удалить дубликат | Проверка должна падать при подмене цели, даже если весь исходник успешно разобран. [Метод](../tac/src/test/kotlin/org/nnezh/lltag/LLTAGCompileExpectationsTest.kt#L844) |
| Проверки внутреннего устройства тестов в серии программ | Пример `a by-value field requires its type first while independent types may move` вручную собирает блоки и проверяет `verifyTypeDeclarations`. Перенести его к матчерам вместе с соответствующим помощником. Отдельно прогнать реальный Bred с обратным порядком объявлений до компиляции C | Обе проверки ценны. Одна доказывает чувствительность проверяющего к ошибке, другая обнаруживает ошибку генератора |
| `CTranspileTest` и корневые нативные тесты | Пересмотреть эталон `transpiles minimal main function`, который буквально требует `return;` внутри `int main`. При исправлении обёртки заменить это ожидание, добавить проверку кода 0 для Unit и 7 для Int. Оставить прямые тесты C-деклараций там, где это часть контракта с C | Текст отдельной инструкции помогает локализовать ошибку. Выполнение программы устанавливает внешний результат |
| `BredCompilationFactoryTest.kt` | Выделить находящийся в нём `CExecutableBuilderTest` в свой файл. У фабрики оставить stdlib, пользовательские ошибки и интеграцию фаз. У builder — пути, владение файлами и результат вызова компилятора. CLI проверять отдельным процессом | Подставной компилятор для ошибок и файловой системы, настоящий MSVC для компоновки и выполнения |
| `LLTACInterpreter` в test-дереве | Поиск по репозиторию находит только объявление класса. Все пять веток `calculate` содержат `TODO()`. Сейчас его можно убрать. Возвращаться к интерпретатору имеет смысл при конкретной задаче исполнения TAC независимо от C | Наблюдаемый результат программ уже можно проверять существующим нативным помощником |

## Какие проверки добавить первыми

| Приоритет | Минимальный сценарий и уровень | Критерий |
|---|---|---|
| 1. Builder, потеря файла | В `@TempDir` заранее записать маркер в `demo.c`, запросить `demo.exe`. Запустить с отсутствующим vcvars, отказом invoker и успешным invoker | Маркер побайтно сохранён во всех трёх случаях. Этой серии не нужен MSVC |
| 2. TAC и наблюдаемое поведение | Затенить счётчик `for` внутренними `val` и `var`. Существующий красный TAC-тест уже сравнивает привязки. Дополнить нативной программой со счётчиком числа проходов и таймаутом | Условие и шаг используют один операнд, программа выполняет две итерации. Отдельный случай с параметром `Off` проверяет, что возвращено его значение |
| 3. Backend и runtime | Скопировать строку из переменной и параметра, сравнить вывод с `hello`. Подать в `readInt` пустой stdin и `abc` перед EOF. Для строковых литералов сравнить байты локального и глобального `é` и встроенного NUL | Здесь нужны stdout, байты, код завершения и таймаут. Расширить существующий нативный помощник возможностью подать и закрыть stdin, получить необработанные байты |
| 4. Представление типов и ABI | Скомпоновать минимальные вызовы опубликованных extern с реальным runtime. Проверить обратный порядок вложенных типов, глобальный скаляр, локальный псевдоним массива. Возврат локального массива проверять диагностикой времени жизни | Для разрешённых программ C собирается и возвращает известный результат. Для запрещённых отказ привязан к Bred-конструкции |
| 5. Договорённость analyzer → TAC | Матрица scalar/array/global для повторов и самоссылки, включая чтение поля в собственном initializer. Для специализации проверить `id(1 < 2)` через публичный путь. Для `return g()` с результатом Unit проверить один вызов и пустой RET | В ошибочной программе предметная диагностика без NPE. В корректной сохранены тип, привязка и число эффектов |
| 6. Прямой вход и фикстуры | Оборванный `STRUCT_DEF`, пропущенный `PARAM`, неверная арность, файл только с типом. Вернуть четыре проверки радара на стабильном ресурсе, учесть `Maybe` из stdlib при корневом запуске | Невалидный IR отклоняется с индексом инструкции, единица только с типами компилируется в объект. Изменение CLI-демо больше не затрагивает радар |

## Как проводить рефакторинг

Сначала закрыть один риск тестом на границе, где виден ущерб. Лучший первый пример — маркер builder. Затем исправить пустое утверждение TAC, устаревшее ожидание глобального массива и пометить нативные проверки JUnit-тегом с отдельной задачей Gradle для запуска на машине с MSVC. Сохранить команду полного прогона, а в отчёте показывать пропуски. Когда ожидаемая нативная конфигурация недоступна в выделенном задании, это должно быть видно как проблема окружения.

После этого переносить тесты по одной теме вместе с её исправлением. Общий помощник подготовки программы полезен для маршрута с одинаковым окружением и фазами. Изолированные тесты прямого AST или TAC должны сохранить возможность подавать вход, который обычный frontend не создаёт. В качестве дополнительной метрики можно агрегировать покрытие Kover по JVM-модулям. Качество нативной части оценивать по исполняемым сценариям и наблюдаемым результатам.
