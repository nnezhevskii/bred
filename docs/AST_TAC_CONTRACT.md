# Контракт АСД → семантический результат → 3AC

Проверенный срез `e965c6e`, ветка `phoenix`, 12 ноября 2026. Область разбора — взаимодействие `parser` и `tac` через `analyzer` и общие модели из `common`. Здесь описаны действующие API, необходимые гарантии и воспроизведённые нарушения на стыке. Формализованные требования ниже предлагаются как проверяемый контракт. Часть из них текущая реализация уже нарушает.

**Основная проблема — между анализом и lowering передаются три независимых объекта: дерево, контекст и таблица типов.** Типы не сохраняют выбранные привязки и сигнатуры, поэтому генератор снова разрешает часть имён. Кроме того, успех анализа ещё не гарантирует, что допустимая форма дерева поддерживается генератором. Это даёт и поздние отказы, и TAC с изменившимся смыслом.

Соседние разборы содержат детали отдельных модулей — [parser](PARSER_REVIEW.md), [analyzer](ANALYZER_REVIEW.md), [форма АСД](AST_REVIEW.md), [корректность TAC](TAC_REVIEW.md), [архитектура TAC](TAC_ARCHITECTURE.md).

## 1. Какие модули фактически участвуют

| Модуль | Ответственность на этом пути | Передаваемые данные |
|---|---|---|
| `lexer` | Разобрать исходник на токены и сохранить позиции | `List<Token>` с EOF |
| `parser` | Построить AST, собрать объявления, разрешить TypeRef, специализировать generic/typeclass | Несколько последовательных `ProgramRoot` и `ProgramGlobalContext` |
| `analyzer` | Проверить области, типы, мутабельность и возвраты | `SemanticAnalysisResult(warnings, expressionTypes)`; дополнительно меняет `isConstructorCalling` у узлов вызова |
| `tac` | Понизить подготовленное дерево в инструкции и метаданные | `List<LLTACElement>` |
| `common` | Определить общие типы, сигнатуры, операнды и инструкции | `TypeSign`, `FunctionSignature`, `Operand`, `LLTACElement` |
| Корневой модуль | Добавить stdlib, связать фазы, оформить ошибки, передать TAC в C backend | `Either<List<String>, List<String>>` для компиляции файла в строки C |

`tac` зависит от lexer, parser, analyzer и common, поскольку в нём есть и lowering, и самостоятельный компилятор исходной строки. `analyzer` зависит от parser. Поэтому перенос общего правила из специализатора в analyzer с обратным импортом из parser создал бы цикл зависимостей. [Зависимости TAC](../tac/build.gradle.kts) · [Зависимости analyzer](../analyzer/build.gradle.kts) · [Результат анализа](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt)

## 2. Действующие API и скрытые предусловия

```kotlin
// Сокращённые сигнатуры существующих API
AbstractSyntaxTreeBuilder.build(tokens): Either<ASTError, ASTNode>
ProgramContextCollector.collect(root): ProgramGlobalContext
ProgramTypeResolver.resolve(root): Either<ASTError, ProgramRoot>
TemplateInstantiator.instantiate(root): Either<ASTError, ProgramRoot>
SemanticAnalyzer.analyzeWithResult(root):
    Either<List<SemanticError>, SemanticAnalysisResult>

LLTACGenerator(
    nameEmitter,
    typeTable: Map<ExpressionASTNode, TypeSign>,
    globalContext: ProgramGlobalContext
).build(root: ASTNode): List<LLTACElement>
```

Формально тип `ASTNode` на входе lowering позволяет подать произвольный узел. Практически генератор ожидает окончательную программу с готовыми объявлениями, развёрнутыми специализациями и фактами анализа именно для её экземпляров выражений. `build` и `visit` публичны, однако доступная через их типы свобода шире фактического контракта.

`expressionTypes` создаётся через `IdentityHashMap`. Метод с возвращаемым типом `Map` сам по себе не сообщает это потребителю. Клонирование дерева, повторный resolver или замена дочернего узла после анализа требуют повторного анализа либо явного переноса соответствующих фактов. Простого равенства деревьев через `equals` недостаточно. [Builder](../parser/src/main/kotlin/org/nnezh/bred/ast/AbstractSyntaxTreeBuilder.kt) · [Resolver](../parser/src/main/kotlin/org/nnezh/bred/context/ProgramTypeResolver.kt) · [Вход генератора](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt)

### Фактическая последовательность

Обозначим R0 разобранным деревом, R1 — деревом после первого resolver, R2 — после специализации, R3 — после окончательного resolver.

```text
токены → R0
C0 = collect(R0)
R1 = resolve(R0, C0)
C1 = collect(R1)
R2 = instantiate(R1, C1)
C2 = collect(R2)
R3 = resolve(R2, C2)
F  = analyze(R3, C2)
IR = lower(R3, C2, F.expressionTypes)
```

Корневой API перед C0 объединяет пользовательский AST и stdlib. `TACCompilerImpl` работает с самостоятельным исходником. Важно, что анализ и lowering используют C2, построенный **до** последнего resolver. Это само по себе ещё не ошибка: необходимо сохранить согласованность деклараций R3 с C2. Проверенные примеры с конкретными суммами эту границу проходят.

В `docs/type_system.md` после финального resolver указан ещё один collector. В обеих реальных точках входа этого вызова нет. Следует привести описание к исполняемому порядку и сформулировать его инвариант. Автоматическое добавление лишнего collector без проверки совместимости типов не обосновано найденными случаями. [Root pipeline](../src/main/kotlin/org/nnezh/BredCompilationFactory.kt) · [TAC pipeline](../tac/src/main/kotlin/org/nnezh/compiler/TACCompiler.kt) · [Описанная последовательность](type_system.md)

## 3. Формальный контракт границы

Пусть R — окончательное дерево, C — согласованный контекст, F — факты анализа. Назовём их одной проверенной программой. Это предлагаемая единица входа lowering; отдельный Kotlin-класс для неё пока отсутствует.

### Предусловия готовности к lowering

| Требование | Что именно должно выполняться | Кто обеспечивает |
|---|---|---|
| Одна версия программы | R, C и F относятся к одному завершённому набору преобразований. После проверки дерево и значимые сведения контекста не меняются | Оркестратор фаз |
| Разрешённые типы | В исполняемых объявлениях и требуемых фактах нет TypeRef или несвязанных generic-параметров. Одного `isResolved` мало: GenericTypeSign тоже помечен resolved | Resolver и специализатор, проверка границы |
| Однозначные привязки | Для чтения и записи известна конкретная локальная, глобальная или параметрическая привязка. Для конструктора известен вид цели | Analyzer и регистрация объявлений |
| Однозначные вызовы | Известны выбранная сигнатура, фактический тип результата, порядок аргументов. Специализации представлены конкретными определениями | Специализатор и analyzer |
| Полные сведения о типах | Конкретные продукты и суммы имеют согласованные поля, конструкторы, варианты и теги. Исходное имя и имя хранения различаются при необходимости | Контекст объявлений и построение layout |
| Типы вычисляемых значений | Для каждого выражения в позиции значения известен тип. Initializer и образец `when` имеют свою роль и не считаются автоматически обычными вычислениями | Analyzer |
| Поддерживаемая форма | Для каждой исполняемой конструкции существует lowering либо заранее дана предметная диагностика ограничения | Явная проверка готовности, вызываемая оркестратором |
| Проверенный поток | Исходное тело и синтетические операции различимы; для допустимых функций установлено требуемое поведение возврата | Analyzer и этап разворачивания |

Сегодня генератор допускает резервное определение типа литерала. Поэтому отсутствие записи для литерала иногда скрывается, а отсутствие записи для `x + 1` вызывает исключение. Это полезная совместимость для прямых вызовов, но её нужно явно описать в тестах низкоуровневого API.

Условия готовности относятся к **исполняемому** дереву. Требование «каждый узел Expression обязан вычисляться» неверно для модели: `A(n)` в ветке суммы — образец и объявление n. В проверенном примере analyzer действительно записал типы образца и его привязки, но эта запись не превращает их в обычный вызов функции и чтение переменной.

### Постусловия результата IR

Для успешного lowering должны выполняться следующие законы.

1. **Сохранение привязки.** Два чтения одного исходного объявления относятся к одному месту хранения. Разные объявления, включая синтетические временные, получают разные идентичности.
2. **Сохранение типа.** Вычисление значения e выдаёт операнд типа F(e). Возвращаемый операнд соответствует типу функции на достижимом пути.
3. **Сохранение цели вызова.** Target и тип результата соответствуют выбранной сигнатуре. Отброшенный результат меняет потребность в destination, а не сигнатуру цели.
4. **Сохранение эффектов.** Вызовы и вычисления индексов выполняются в установленном языке порядке и количестве. Для текущего энергичного вычисления логических операндов применяется фактический контракт G-89; переход к короткому замыканию — отдельное решение языка.
5. **Полнота определения.** Для каждой достижимой ссылки есть параметр, локальное/глобальное хранение, определение функции, конструктор или явно объявленный extern. Глобальный scalar не должен исчезать только из-за формы AST.
6. **Корректность потока.** Переходы адресуют метки своей функции; допустимые значения доходят до return. Синтетический недостижимый `RET Unit` после возвращающих ветвей отличать от достижимого неправильного возврата.
7. **Согласованность layout.** Объявление типа, создание значения и чтение поля используют одни метаданные. Имена хранения полей и переменных уникальны в целевой области.
8. **Предметная ошибка.** Неподдерживаемый исходник даёт диагностику с конструкцией и стадией. Несогласованные R/C/F — нарушение API. Отсутствие runtime-значения у Unit — ожидаемое свойство типа.

В формальной форме желаемая гарантия выглядит так:

```text
Ready(R, C, F) ⇒
    lower(R, C, F) выдаёт IR, сохраняющий привязки, типы и эффекты.

SemanticSuccess(R, C) сам по себе сейчас не доказывает Ready(R, C, F).
```

## 4. Воспроизведённые нарушения

### 4.1. Ссылка на параметр переосмысляется как конструктор

```bred
type Flag = Off | On
fun f(Off: Int): Int { return Off }
```

Полный подготовительный путь вернул успешный анализ. TAC получился таким:

```text
func f:
  GET_PARAM Off:Int
  CALL var1:Flag Off:Flag 0:Int
  RET var1:Flag
```

Нарушены сохранение привязки и типа. Analyzer правильно предпочёл параметр, но не передал выбранное объявление. Ветка VariableExpression в генераторе снова ищет конструктор без аргументов по имени. Root API со stdlib тоже вернул Right с C-кодом. Контроль исправления — обычный `Off` без затенения по-прежнему создаёт вариант, а эта функция возвращает Int-параметр. [Анализ имени](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt) · [Повторный поиск](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACExpressionSubgenerator.kt)

### 4.2. Проверенный доступ к полю получает тип из другой области

```bred
type P(x: Int)
type Q(y: Int)
fun f(p: P): Int {
    if (true) { val p: Q = Q(0) }
    return p.x
}
```

Анализ успешен с допустимым затенением. Lowering завершился `type 'Q' has no field 'x'`. Собственный `localVariableTypes` генератора перезаписан внутренним объявлением, после блока не восстановлен. Проверка поля и типа корня повторяет работу analyzer с другим состоянием. Root API вернул Left с префиксом `TAC generation failed`.

**Действие.** Передавать разрешённый корень и цепочку полей. Исправление только словаря восстанавливает тип, но ещё не гарантирует отдельное хранение двух p. Регрессии нужны на разные типы и на одинаковые типы с чтением после блока. G-80. [Словарь lowering](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt) · [fieldAccessTarget](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACExpressionSubgenerator.kt)

### 4.3. Успешная типизация Unit-when не означает поддержку этой формы

```bred
fun f(n: Int): Unit {
    return when (n) {
        0 -> { println("zero") }
        else -> { println("other") }
    }
}
```

Parser принимает выражение, analyzer назначает ему Unit и принимает return. Lowering бросает `when expression TAC lowering is not supported yet`. Тот же отказ получен из root API. Документ `ast_to_3ac_generation.md` утверждает, что неподдерживаемое value-producing использование when уже отвергнуто analyzer. Этот пример показывает пропуск: Unit-результат проходит проверку совместимости типов.

**Действие.** Для нынешнего ограничения диагностировать такую позицию до lowering либо поддержать эффектный when при возврате Unit. Это не требует обещать значение Int/Double для when. Контроль — statement-when продолжает работать. G-71 связан, но не описывает конкретную дырку допуска. [When в analyzer](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt) · [Выражения lowering](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACExpressionSubgenerator.kt) · [Заявленная гарантия](ast_to_3ac_generation.md)

### 4.4. Unit и отбрасывание значения не имеют собственного контракта

```bred
fun g() {}
fun f() { return g() }
```

Анализ успешен. Получено `CALL var1:Unit g:Unit 0:Int → RET var1:Unit`. Генератор требует результирующую переменную даже там, где нужно выполнить эффект и вернуть Unit. Для другой программы `fun g(): Int { return 7 } fun f() { g() }` получено `CALL g:Unit 0:Int`. Отсутствие destination допустимо, но тип цели Int потерян.

**Действие.** Разделить тип цели вызова и наличие сохраняемого результата. В lowering различить «получить значение» и «выполнить ради эффектов». Проверка — ровно один CALL, корректная сигнатура, Unit-return без переменной. Обе программы из root API сейчас возвращают Right с C-кодом. Нативное выполнение в этой задаче не проводилось. [Call statement и return](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt) · [Контракт результата выражения](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACExpressionSubgenerator.kt)

### 4.5. Глобальные значения анализируются шире, чем понижаются

```bred
val limit: Int = 7
fun f(): Int { return limit }
```

Анализ успешен, в IR осталось только `RET limit:Int` без определения limit. Root API вернул Right с `return limit;`. Это потеря объявления между двумя стадиями, G-79.

Для `val nums: Int[1] = [-1]` анализ тоже успешен, но lowering отказал на UnaryExpression с `unsupported global Int array initializer expression`. Размер и тип элементов проверены, форма константного выражения не согласована с потребителем. G-61.

**Действие.** У scalar обеспечить хранение или допустимую подстановку. Для ограниченной формы global initializer проверить её до emission либо добавить поддерживаемые константные операции. Типизируемость и возможность представления глобального инициализатора — разные гарантии. [Глобальные узлы](../parser/src/main/kotlin/org/nnezh/bred/ast/AST.kt) · [Lowering globals](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt)

### 4.6. Три API-параметра позволяют незаметно смешать версии дерева

На `fun f(x: Int): Int { return x + 1 }` получены окончательные R, C и F. Затем R скопировано штатным `AstCloner.cloneSubtree`. Проверка показала `clone !== R` при `clone.equals(R) == true`. Вызов lowering копии с прежними C/F завершился `missing semantic type for expression 'x + 1'`.

Это **проверка нарушения предусловия прямым клиентом API**. Штатный pipeline передаёт одно и то же дерево в анализ и lowering. Проблема в том, что API не выражает принадлежность фактов дереву; равная по содержимому копия выглядит допустимым аргументом.

**Действие.** Объединить финальный root, context и analysis в результат подготовительного прохода. Анализировать после последнего преобразования. При намеренной замене дерева явно аннулировать прежние факты. Один лишь перевод IdentityHashMap в обычный HashMap не восстанавливает привязки и не решает мутацию узлов. [AstCloner](../parser/src/main/kotlin/org/nnezh/bred/ast/AstCloner.kt) · [Таблица анализа](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt)

## 5. Какие сведения теряются или недостаточно представлены

| Сведения до границы | Что получает TAC | Чем это грозит |
|---|---|---|
| Конкретная lexical-привязка | Лексема и тип | Затенение и совпадение с конструктором переосмысляются |
| Выбранная сигнатура вызова | Имя, факты о типе выражения и изменяемый boolean конструктора | Повторный выбор цели, потеря типа при discarded-result |
| Проверенный образец when | Исходная форма Variable/FunctionCall и общие метаданные | Lowering повторяет распознавание варианта и привязку полей |
| Решение о мутабельности | Проверенное присваивание и строковое имя | Для текущего emission достаточно доверять проверке; новый проход должен понимать, какое хранение изменено |
| Результат flow-проверки | Тело с explicit/synthetic return | Следующая стадия заново трактует хвост функции |
| Позиции и происхождение | Частично сохранённые Token/LocatedOperator, строки имён | Ошибка lowering показывает сводку выражения, связь с исходной декларацией ослабевает |
| Warnings | Поле SemanticAnalysisResult | Оба компилятора используют expressionTypes и не возвращают warnings клиенту |
| Одна версия контекста и AST | Независимые изменяемые объекты | Изменение объявления или мутация контекста после анализа не аннулируют факты автоматически |

`FunctionCallExpressionASTNode.isConstructorCalling` в модели уже существует, analyzer его меняет. В lowering вызовов этот признак не используется для явной передачи вида цели в IR. Для bare VariableExpression такого признака вообще нет. Это пример недостаточной передачи решения, которое уже принято на предыдущей стадии. [Модель выражений](../parser/src/main/kotlin/org/nnezh/bred/ast/ASTNode.kt) · [Вызовы analyzer](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt)

## 6. Дублирование работы и недостаточные проверки

**Оркестрация повторяется.** Root compiler, TACCompiler и помощник тестов с инстанцированием повторяют сбор контекста, два разрешения и специализацию. Сами повторные разрешения нужны из-за появившихся конкретных объявлений; цена поддержки возникает из-за нескольких копий порядка фаз. Общий проход от собранного ProgramRoot до проверенной программы может жить в слое, имеющем зависимости от parser и analyzer. Загрузка stdlib и публичные формы ошибок остаются у адаптеров. G-88. [Root](../src/main/kotlin/org/nnezh/BredCompilationFactory.kt) · [TAC](../tac/src/main/kotlin/org/nnezh/compiler/TACCompiler.kt) · [Тестовый pipeline](../analyzer/src/test/kotlin/org/nnezh/SemanticAnalyzerTestSupport.kt)

**Повторная семантика даёт разные ответы.** Analyzer и lowering отдельно ищут корень доступа к полю и интерпретируют образец when. Специализатор имеет собственный inferType бинарной операции. Проверка `id(1 < 2)` из предыдущего разбора показывает расхождение с TypeValidator ещё до границы lowering. Первым общим правилом может стать тип оператора от типов операндов; общей зависимостью нельзя делать обратный импорт analyzer в parser. [Специализация](../parser/src/main/kotlin/org/nnezh/bred/codegenerator/TemplateInstantiator.kt) · [TypeValidator](../analyzer/src/main/java/org/nnezh/TypeValidator.kt)

**Проверка полноты входа размыта.** Генератор по продукту допускает `productFields(...).orEmpty()`, по сумме пропускает emission при отсутствующей definition, в общем visit имеет `else -> {}`. Игнорирование raw typeclass после специализации может быть намеренным. Потеря metadata конкретного исполняемого типа должна различаться с ним. Это риск по чтению кода для неполного входа; в обычном pipeline отдельный сбой метаданных этим способом не воспроизводился.

**Имена временных и синтетических переменных пересекаются с исходными.** В прежних проверках parameter `var3` был перезаписан временной TAC, а parser создал `_right_borderi` поверх одноимённого пользователя. Оба дефекта нарушают один сквозной контракт идентичности, хотя возникают на разных этапах. Одно место выдачи уникальных печатных имён поможет после сохранения идентичностей. [Пример var3](TAC_REVIEW.md) · [Пример for](PARSER_REVIEW.md)

**Поддержка операции не равна поддержке типа.** Прямая таблица типов может сказать Unit для when, Array<Int> для ссылки или String для сравнения. Готовность lowering также зависит от роли выражения, вида хранения и контрактов runtime. Отдельная проверка готовности делает отказ до emission предметным, а сохранение цели и типа операции позволяет backend выбрать нужное представление.

## 7. Предлагаемый минимальный API

Схема ниже показывает обязанности. Это предложение интерфейса, код в репозитории по ней не изменён.

```kotlin
// Схема, не готовое объявление для вставки в проект
data class CheckedProgram(
    val root: ProgramRoot,
    val context: ProgramGlobalContext,
    val analysis: SemanticAnalysisResult
)

fun prepare(root, environment): Either<Diagnostics, CheckedProgram>
fun lower(program: CheckedProgram): Either<LoweringDiagnostics, TacProgram>
```

Первый шаг — объединить существующие три объекта и выдавать их после окончательного resolver и анализа. Публичное создание произвольного несогласованного набора нужно ограничить фактическим владением результата. Далее постепенно расширять analysis фактами о привязках, вызовах и образцах. Одной обёртки недостаточно для неизменяемости: mutable functions и словари context остаются точками изменения.

`TacProgram` на первом шаге может содержать нынешний список инструкций. Типизированные обращения к привязкам и явные аргументы вызова можно вводить по одному виду операции. Конкретный новый класс на каждую стадию оправдан, когда он действительно делает недопустимую комбинацию недоступной или проверяет её при создании.

Разделить диагностики по причине: ошибка исходника, неподдерживаемая форма на этой стадии, несогласованная проверенная программа, внутренняя ошибка компилятора. Существующие API могут адаптировать их к прежнему Either или исключению. Текстовое совпадение ошибки полезно для совместимости клиентов, но не должно быть единственным способом узнать стадию.

## 8. Что проверено и какой набор регрессий нужен

### Выполнено на текущем срезе

Повторный `:parser:test :analyzer:test :tac:test --offline --rerun-tasks --continue` — **305 успешных из 307**. Parser 103/105, analyzer 152/152, tac 50/50. Два падения parser по-прежнему связаны с фикстурой G-74. Через локальный JShell отдельно проверены успешный анализ и последующий lowering десяти программ, контрольная копия AST и таблица типов образца when. Для восьми программ дополнительно проверен root API со stdlib. Нативная сборка здесь не запускалась.

Контроли важны: `return x + 1` при обычном имени x понижается корректно; конкретная сумма `S = A(n: Int) | B` со statement-when даёт теги, payload-load и переходы. Пример `val b: Array<Int> = a; return b[0]` сохраняет alias и LOAD в TAC; дальнейшее объявление указателя в C — отдельный контракт backend, этот результат не доказывает поддержку всего пути.

### Рекомендуемые проверки контракта

| Сценарий | Проверять до lowering | Проверять в IR или результате |
|---|---|---|
| Off как параметр при наличии варианта Off | Выбрана привязка параметра Int | Нет конструкторного CALL, RET Int |
| Затенённый продукт с другим набором полей | После блока корень снова внешний P | LOAD_FIELD относится к внешнему хранению |
| Unit-return g() | Цель g возвращает Unit | Один CALL без значения и пустой RET |
| Отброшенный g(): Int | Сигнатура остаётся Int | Destination отсутствует, тип цели Int |
| Unit-when в return | Явный допуск реализации либо диагностика ограничения | При допуске выполнены эффекты выбранной ветки |
| Глобальный limit | Привязка и начальное значение доступны | Есть определение или доказанно допустимая подстановка |
| Глобальный [-1] | Проверена форма константного выражения | Поддержанный initializer либо ранняя диагностика |
| Копия проанализированного AST | Прежние факты аннулированы | Предметная ошибка принадлежности либо повторный анализ |
| Параметры Int[] и Array<Int> | Одинаковый эффективный тип параметра | Одинаковая сигнатура GET_PARAM |
| Изменение дерева между фазами | Выявлена устаревшая analysis | Lowering не продолжает работу со старой таблицей |

Нужны сравнения самих типов и целей операций. Проверка, что pretty-printed строка не содержит `TypeRef`, не доказывает отсутствие незавершённого типа в объекте: принтер может выводить только `type.name`. Тест `user function calls use mangled target name` сейчас вычисляет TAC без утверждения о цели вызова. [Тесты TAC](../tac/src/test/kotlin/org/nnezh/lltag/LLTAGCompileExpectationsTest.kt) · [Печать операнда](../common/src/main/kotlin/org/nnezh/ICGenerator/Operand.kt)
