# Архитектура 3AC в Bred

Срез `09472ab`. Здесь критерий качества — стоимость следующего изменения. Можно ли добавить вызов, проверить использование переменной или изменить представление суммы, опираясь на явно описанные свойства IR? Фактические программы и дефекты вынесены в [ревизию корректности](TAC_REVIEW.md). Ниже — разбор по исходникам. Оценка сложности копирования списков аналитическая, замеров производительности не проводилось.

**Главная трудность — смысл инструкции распределён между тем, кто её создал, и тем, кто её читает.** Например, чтобы установить, что записывает `destination`, нужно знать opcode. Чтобы узнать аргументы вызова, нужно посмотреть назад по потоку. Чтобы отличить временную переменную от пользовательской, имеющихся данных иногда вообще недостаточно. Пока потребителей два — C backend и принтер — эти договорённости можно держать в голове. Следующий проход, даже простой поиск неиспользуемых значений, вынужден будет восстанавливать их ещё раз.

## 1. Поле destination выглядит как определение переменной, но у него несколько ролей

У `ADD` это место записи. У `PARAM` там хранится читаемый аргумент. У `STORE` — массив, содержимое которого меняется. У `JMP` — метка. У `STRUCT_DEF` — объявляемый тип. Видно конкретное последствие: `CTranspile.parseFunction` ищет локальные объявления по `destination` и поддерживает список исключений по opcode. При добавлении инструкции автору нужно знать ещё и про этот список.

**Вердикт — улучшать сейчас при касании этих операций.** Первый шаг — описать непосредственно в модели, какие скалярные значения инструкция читает и определяет, какие объекты памяти изменяет. Для `STORE a[i] = v` чтения включают индекс и значение, запись относится к памяти массива. Тест на `PARAM` должен показывать чтение без объявления новой переменной. Когда роли существенно отличаются, выгодны отдельные формы инструкции, например вызов и запись в поле. Общая форма для семейства `ADD/SUB/MUL` вполне удобна. [Фабрики инструкций](../common/src/main/kotlin/org/nnezh/ICGenerator/LLTACInstruction.kt) · [Поиск локальных переменных](../c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt)

## 2. Операнд теряет своё происхождение слишком рано

`Operand.Variable(name, type)` представляет локальную переменную, временную, а в отдельных инструкциях ещё имя поля, имя варианта или готовый путь вроде `person.address`. При переименовании локальной `address` проходу пришлось бы заново разбираться, в каком месте это переменная, а в каком — сегмент пути. Коллизия параметра `var3` с временной уже показала цену потери этой информации.

**Первый рефакторинг, который я бы взяла.** Начать с различия «привязка исходной программы / временное значение». Тождество привязки определяет анализатор, временное значение создаёт генератор, читаемое имя выдаёт принтер. Затем отдельно представить обращение к полю как корень и последовательность полей. Это также пригодится при добавлении `fighters[i].score`: у такого обращения корнем служит результат загрузки элемента. Проверить отдельно коллизию `var3` и прежнюю генерацию доступа `person.address.city`. [Операнды](../common/src/main/kotlin/org/nnezh/ICGenerator/Operand.kt) · [Разбор цепочки полей](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACExpressionSubgenerator.kt)

## 3. Контракт генерации выражения перекладывает решения на вызывающий код

`buildInstructionsForExpression(variable, type, expression)` принимает желаемое имя результата и тип, хотя генератор также имеет таблицу типов. В ответ возвращаются список инструкций, nullable-имя и ещё один тип. При чтении переменной генератор возвращает исходное имя. При чтении элемента массива создаёт свою временную. Литерал записывает в предложенное место. Поэтому объявление, присваивание и запись по индексу по-разному сверяют запрошенное и фактическое место и при необходимости добавляют `ASSIGN`. При вызове ради эффекта передача `Unit` уже привела к потере фактической сигнатуры.

**Менять вместе с работой над вызовами и возвратами.** Внутренний интерфейс может различать «вычислить и получить типизированный операнд» и «выполнить ради эффектов». Запись результата прямо в переменную оставить локальной оптимизацией. Переход начать с `return g()` при `g(): Unit` и отброшенного вызова `get(): Int`. Затем вынести общее чтение типа: `tacType` и резервное определение типов литералов сейчас продублированы в обоих генераторах. Проверка границы — побочный эффект выполняется ровно один раз, вызывающий код больше не собирает тип и имя результата из отдельных частей. [Генератор выражений](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACExpressionSubgenerator.kt) · [Объявления, присваивания и возвраты](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt)

## 4. Линейный список хорошо описывает выполнение, хуже — структуру программы

Тело цикла естественно читать как метку, условный переход, инструкции и обратный переход. У заголовка функции и вызова другие потребности. Параметры функции определяются по следующим `GET_PARAM`, аргументы вызова — по предыдущим `PARAM`. Метаданные суммы тоже разложены по потоку. На стороне C появились отдельные обходы для заголовков, структур и вариантов. Эти проходы ясны и сами по себе дёшевы. Издержка — несколько мест должны одинаково понимать границы записей.

**Первый оправданный шаг — вызов с собственным списком аргументов.** Для `f(g(x), h(y))` сначала вычислить вложенные вызовы в существующем порядке, затем создать вызов `f` с двумя готовыми операндами. Принтер может по-прежнему отображать `PARAM` и `CALL`. Тогда вставка отладочной позиции перед вызовом не меняет, какие аргументы увидит backend. При добавлении второго потребителя метаданных полезно сгруппировать функции с параметрами и телом, глобальные значения и определения типов на уровне программы. Тела функций могут оставаться линейными. [Сборка аргументов](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACExpressionSubgenerator.kt) · [Чтение потока](../c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt)

## 5. Время жизни состояния генератора скрыто в порядке обхода

`build(root: ASTNode)` и `visit(node)` публичны. Однако осмысленный вызов зависит от экземпляра проанализированного дерева, таблицы типов, контекста, текущей функции, заполнения `localVariableTypes` и состояния счётчиков. Подгенератор получает два callback для чтения изменяемых карт владельца. Очистка списка типов делается на входе в функцию, временное добавление payload-привязок — внутри `when`, счётчики живут весь срок жизни генератора. Поэтому вставка выражения в раннюю функцию может перенумеровать временные во всех следующих функциях. Обычные точки входа создают свежий генератор; оценка риска повторного использования относится к более широкому публичному API.

**Небольшое изменение.** Оставить публичным вход уровня проанализированной программы, сделать рекурсивный обход внутренним, передавать состояние текущей функции явно. В состоянии функции естественно держать генератор временных и меток. При смене нумерации заранее отделить ожидаемый шум снимков от изменений семантики. Полезная проверка — добавление локального выражения в функцию `a` сохраняет структуру IR независимо компилируемой функции `b`. [Состояние и обход](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt) · [Точка входа](../tac/src/main/kotlin/org/nnezh/compiler/TACCompiler.kt)

## 6. Генератор одновременно выбирает смысл конструкции и понижает её

Показателен `when`. Семантическая стадия уже определила вариант суммы, проверила его поля и привязки. Генератор снова разбирает форму условия, ищет вариант, формирует имена полей, добавляет привязки в таблицу, выпускает переходы и восстанавливает состояние. Похожая ситуация у ссылок на конструктор. Расширение образцов затронет обе интерпретации синтаксиса.

**Когда возвращаться.** При следующем расширении `when` передавать для ветки разрешённый вариант и привязки из результата анализа. В lowering остаётся отдельная, хорошо тестируемая задача: сравнить тег, загрузить поля, перейти к нужному блоку. Сведения о физическом расположении полей суммы стоит собрать в одном месте, которым пользуются объявление типа, конструктор и извлечение payload. Можно начать с одной ветки `Just(value)` и сравнить её 3AC до и после. [Проверка образца](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt) · [buildWhenStatement и layout суммы](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt)

## 7. Построение списков может плохо масштабироваться на глубоко вложенных выражениях

Каждое бинарное выражение создаёт свой список и копирует в него ссылки на инструкции обоих дочерних выражений через `addAll`. У левоассоциативной цепочки `a + b + c + …` инструкции левой части перекладываются снова на каждом уровне. Для цепочки из n слагаемых сумма объёмов таких копирований может расти как O(n²), даже когда итоговый TAC растёт линейно. Глубоко вложенные блоки используют похожий шаблон `addAll(visit(...))`.

**Пока оставить, если реальные программы компилируются достаточно быстро.** Когда появятся длинные сгенерированные выражения, замерить именно lowering на заранее разобранном дереве нескольких размеров, отдельно от парсинга и анализа. При заметной цене писать инструкции в один буфер функции, а из генерации выражения возвращать только результат. Проверка миграции — прежний порядок чтений и эффектов, особенно у аргументов и присваиваний в массив. Такой буфер избавляет от повторного копирования; глубина рекурсии остаётся самостоятельным вопросом. [Бинарные выражения и вызовы](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACExpressionSubgenerator.kt) · [Обход блоков](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt)

## 8. Модель IR отвечает за два разных текстовых формата

`Operand.LongConst.asRightValue()` добавляет C-суффикс `LL` уже в `common`. Снимки, в свою очередь, зависят от `toString()` у операндов, инструкций и opcode: `PrettyPrinter` в основном добавляет отступы. Поэтому изменение диагностического представления объекта способно изменить эталоны, а C-специфичное решение оказывается доступно каждому потребителю IR. Например, снимок обычной переменной печатает `type.name`, возврат — `type.render()`. У массивов эти способы показывают разную детализацию типа.

**Когда возвращаться.** Если меняется формат снимка, перенести форматирование этой формы в `PrettyPrinter` и проверить один эталон специально на читаемость. Если меняются C-литералы или появляется другой backend, перенести C-рендеринг в `c-backend`. Модель хранит числовое значение и тип. Для корректности типизации полезнее сравнивать операнды напрямую; для ветвлений по-прежнему ценен читаемый текстовый снимок. [Операнды](../common/src/main/kotlin/org/nnezh/ICGenerator/Operand.kt) · [PrettyPrinter](https://github.com/nnezhevskii/bred/blob/09472ab043c817532dc8ca729cd12c86b923d483/tac/src/main/kotlin/org/nnezh/ICGenerator/PrettyPrinter.kt) · [Сравнение снимков](https://github.com/nnezhevskii/bred/blob/09472ab043c817532dc8ca729cd12c86b923d483/tac/src/test/kotlin/org/nnezh/lltag/LLTAGSnapshotTester.kt)

## Что оставить в покое

- **Разделение statements и expressions.** Оно соответствует разным результатам работы. Основная трудность сосредоточена в контракте возврата значения и совместном состоянии. Простая нарезка большого `when` на классы по узлу AST сохранит обе проблемы.
- **Линейные переходы и метки.** Для текущих `if`, `while` и развёрнутого `for` они прозрачны. Граф базовых блоков станет оправданным, когда конкретному проходу потребуется достижимость, анализ потока данных или оптимизация между блоками. Его можно строить поверх линейного тела по запросу.
- **Текущие границы Gradle-модулей.** Модель IR в `common` уже позволяет `c-backend` получать инструкции без зависимости от парсера и анализатора. Отдельный модуль IR имеет смысл, если появится новый потребитель или зависимость `common` начнёт тянуть лишние компоненты. Сегодня больший эффект дадут типы операндов и явная структура вызова. ## Порядок работ

| Когда | Первая граница изменения | Как понять, что этого достаточно |
|---|---|---|
| Первой задачей | Развести привязку и временную в одной функции | Пример с параметром `var3` сохраняет значение; по IR видно происхождение обоих операндов. |
| Следом | Развести значение, эффект и место записи у вызовов | Отброшенный `Int` сохраняет сигнатуру функции, `Unit`-вызов выполняется один раз без переменной. |
| При следующем изменении вызовов | Собрать аргументы в объекте вызова | Вложенные вызовы сохраняют порядок; backend читает аргументы прямо из операции. |
| При расширении сумм или образцов | Передать проверенный вариант и привязки | Генератор строит переходы и извлечение полей без повторного выбора варианта по AST. |
| По наблюдаемой потребности | Буфер эмиссии, форматтер, группировка функций или граф блоков | Для каждого изменения есть свой повод: замер, требование к формату или конкретный потребитель. |

Для короткой первой сессии достаточно описать на бумаге три операнда одной инструкции `ADD` для `fun f(var3: Int): Int { return var3 + 1 }`: кто создал каждый операнд, какой у него тип и где определяется его имя. Этот пример даёт критерий для выбора модели ещё до работы над Kotlin-кодом.
