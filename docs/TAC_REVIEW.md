# AST → 3AC. Ревизия выхода фронтенда

**12 ноября 2026 · `09472ab`.** Штатные тесты модуля зелёные. При этом генератор способен принять семантически проверенную функцию и изменить значение параметра, тип возврата или смысл обращения к имени. Первым я бы закрыла коллизию `var3`, затем передачу выбранного объявления и представление вызовов. Все три проблемы видны уже в TAC, до генерации C.

## Граница модуля и способ проверки

Публичная точка входа `TACCompilerImpl.compile(String)` принимает исходник, выполняет разбор, разрешение типов, специализацию, повторное разрешение и семантический анализ. Непосредственный вход `LLTACGenerator` — экземпляр AST, таблица типов выражений и глобальный контекст. Ключи в таблице типов сравниваются по идентичности объектов. На выходе — линейный список `LLTACElement` с объявлениями, метками и инструкциями. Модель операндов и инструкций физически лежит в `common`. Корневой компилятор тоже вызывает генератор, но предварительно подключает `stdlib.bred`. ## Дефекты по убыванию последствий

### 1. Временная переменная перезаписывает параметр пользователя

```bred
fun f(var3: Int): Int { return var3 + 1 }
```

Фактический TAC:

```text
func f:
  GET_PARAM var3:Int
  ASSIGN var3:Int 1:Int
  ADD var1:Int var3:Int var3:Int
  RET var1:Int
```

Для аргумента 7 исходник задаёт 8. По этим инструкциям получается 2. `TACNameEmitter.nextVar()` выдаёт обычные строки `var1`, `var2`, `var3`, а имена параметров и локальных переменных попадают в то же пространство. В контрольном примере с именем `var2` эта конкретная последовательность корректна — результат зависит даже от номера, выбранного автором программы. Коллизия возникает внутри единственной области видимости, независимо от G-80.

**Исправление и проверка.** Различать в модели временный операнд и привязку исходной программы. Назначать уникальные печатные и C-имена при отображении. Для небольшого первого исправления допустим аллокатор, резервирующий все имена функции до выдачи временных. В тесте проверить операнды `ADD` и отсутствие записи в параметр. Добавить случай с именем локальной переменной, объявленной позже в функции. [TACNameEmitter](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt) · [Операнды](../common/src/main/kotlin/org/nnezh/ICGenerator/Operand.kt)

### 2. Параметр превращается в конструктор, меняется тип RET

```bred
type Flag = Off | On
fun f(Off: Int): Int { return Off }
```

Получено `GET_PARAM Off:Int → CALL var1:Flag Off:Flag 0:Int → RET var1:Flag`. Анализатор успешно разрешил чтение параметра и принял возвращаемый `Int`. Ветка `VariableExpressionASTNode` при генерации заново ищет единственный конструктор без аргументов по написанию имени и выбирает его. Здесь конструктор однозначен, поэтому одной диагностики неоднозначности конструкторов из G-72 недостаточно.

**Исправление и проверка.** Передавать из семантического анализа выбранное объявление для каждого употребления имени. Для данного исходника ожидается `RET Off:Int` без `CALL`. Контроль — функция `fun off(): Flag { return Off }`, где конструктор действительно нужен. Инвариант для проверки IR — тип значения каждого достижимого `RET` согласован с типом функции. [Анализ имени](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt) · [Генерация выражений](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACExpressionSubgenerator.kt)

### 3. Поля разных вариантов суммы получают один идентификатор

```bred
type S = A_B(c: Int) | A(B_c: Long)
fun f() { }
```

В одном `STRUCT_DEF S` выданы `FIELD A_B_c:Int` и `FIELD A_B_c:Long`. Обе записи `SUM_VARIANT_FIELD` тоже ссылаются на `A_B_c`. Разные пары «вариант, поле» совпали после склейки через подчёркивание. В C-структуре имена членов должны быть уникальны. Проблема уже содержится в метаданных IR.

**Исправление и проверка.** Хранить пару «вариант, поле» структурно либо выдавать гарантированно уникальное имя хранения из таблицы layout типа. Конструктор и извлечение payload в `when` должны пользоваться одним отображением. Проверить уникальность полей и оба направления — создание каждого варианта и чтение именно его значения. [Построение layout и payloadLoads](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt) · [Потребитель метаданных](../c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt)

### 4. Тип затеняющей переменной переживает выход из блока

```bred
type P(x: Int)
type Q(y: Int)
fun f(p: P): Int {
    if (true) { val p: Q = Q(0) }
    return p.x
}
```

Публичный путь проходит семантику, затем бросает `LLTACGenerationException: type 'Q' has no field 'x' at expression 'p.x'`. Словарь `localVariableTypes` очищается при входе в функцию. Обход `BlockAstNode` посещает дочерние инструкции без восстановления прежних типов. Для payload-привязок `when` отдельно написано сохранение и восстановление. Это дополнительное проявление G-80: генерация способна оборваться ещё до C.

**Исправление и проверка.** Передавать в lowering разрешённый корень доступа к полю и типы звеньев цепочки. Локальное восстановление словаря после блока исправит выбор типа, но сама привязка тоже должна получить отдельное место хранения. Проверить `return p.x` после блока, чтение `p.y` внутри него и прежний случай двух скаляров одинакового типа. [Обход блоков](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt) · [fieldAccessTarget](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACExpressionSubgenerator.kt)

### 5. Выражение типа Unit материализуется как переменная

```bred
fun g() { }
fun f() { return g() }
```

Получено `CALL var1:Unit g:Unit 0:Int → RET var1:Unit`. Проверен и следующий этап: в тексте тела C-функции появляются `void var1;`, `var1 = g();`, `return var1;`. Для принятого исходника корректное понижение — один вызов ради эффекта и `RET Unit` без операнда.

**Исправление и проверка.** Разделить результат «есть операнд со значением» и «эффект выполнен». Сейчас `LLTACExpressionSubgeneratorResult` хранит `finalVariable: String?`, а обработчик `return expr` запрашивает временную и использует `finalVariable!!`. Проверить однократность вызова и отсутствие `Operand.Variable` с типом `Unit` в этом случае. [Возврат из функции](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt) · [Модель CALL и RET](../common/src/main/kotlin/org/nnezh/ICGenerator/LLTACInstruction.kt)

### 6. Отбрасывание результата стирает возвращаемый тип и вид вызова

Для `fun get(): Int { return 9 } fun f() { get() }` получено `CALL get:Unit 0:Int`. Отсутствие destination верно, но реальная сигнатура `get` возвращает `Int`. Для `type Pair(x: Int) fun f() { Pair(1) }` получено `PARAM var1:Int → CALL Pair:Unit 1:Int`. C backend напечатал `Pair(var1);`, хотя `Pair` объявлен как typedef структуры. Backend узнаёт конструктор по типу destination, который в такой инструкции отсутствует.

**Исправление и проверка.** Хранить отдельно выбранную цель (функция или конструктор), её тип результата и необязательное место записи. Для отброшенного конструктора сохранить эффекты вычисления аргументов. Контрольный случай — `Pair(readInt())`: ввод должен произойти один раз независимо от дальнейшей оптимизации создания значения. [Вызов-инструкция](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt) · [Восстановление цели из CALL](../c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt)

## Какие контракты усилить на выходе фронтенда

1. **Один согласованный вход.** `build(root: ASTNode)` принимает произвольный узел, контекст и таблица типов передаются отдельно. Объединить окончательный `ProgramRoot`, его контекст и результат анализа в один аргумент публичного lowering. Обход узла оставить внутренней деталью. Так копия дерева после анализа не получит случайно таблицу от другого экземпляра. Ветки `else -> {}`, `productFields(...).orEmpty()` и пропуск суммы при отсутствующем определении различать по назначению: ожидаемая шаблонная декларация и потерянные метаданные конкретного типа требуют разных решений. Это риск по коду при неполном входе, отдельно от воспроизведённых дефектов.
2. **Различать имена и роли операндов.** Имя переменной, путь `person.address` и имя поля сейчас могут быть представлены `Operand.Variable`. В `storeField` поле передаётся как переменная, у `CALL` аргументы восстанавливаются по соседним `PARAM`. Начать с явных привязок и временных, затем оформить цель и аргументы вызова. Существующий текстовый формат можно сохранить на уровне pretty-printer. Это позволяет развивать IR небольшими изменениями.
3. **Проверять инварианты непосредственно у инструкций.** Для первой версии тестового валидатора достаточно проверить тип возврата, существование цели перехода внутри функции, уникальность имён полей одного layout и соответствие сигнатур вызовов. В `Unit`-функции разрешён пустой возврат. Для non-Unit учитывать достижимость: parser может добавлять хвостовой синтетический `RET Unit` после веток, которые уже вернули значения. Тест коллизии временных отдельно проверяет исходную привязку: два разных объекта уже невозможно восстановить после склейки в одно имя.
4. **Оставить представление управляемым.** Линейные переходы уже выражают `if`, `while` и развёрнутый `for`. В проверенном `a[b[0]] = 5` индекс сначала загружается, затем сохраняется во временную, и `STORE` использует сохранённое значение. При смене представления операндов сохранить порядок вычислений, включая вложенные вызовы. Ввод SSA для перечисленных исправлений не требуется.

## Задачи для возвращения

- **10–15 минут.** Воспроизвести `f(var3)` и написать один падающий тест по объектам инструкций: параметр участвует в сложении с отдельным временным операндом для единицы. На этом можно остановиться.
- **Одна небольшая правка.** Разобрать конфликт временных имён. Проверить исходный пример, вариант `var2` и локальное имя из конца тела. Посмотреть изменения в существующих снимках.
- **Одна изолированная задача на контракт.** Закрепить `return g()` для `Unit`-функции — один `CALL` без destination и один пустой `RET`. Затем отдельно заняться отброшенным результатом типа `Int`.
- **Когда захочется поработать с тестовой базой.** Взять один исключённый `whileCountdown`, заменить устаревший вызов преобразования строки и вручную сверить границы цикла, ветвление и возвращаемое значение. Пройденный пример вернуть в активный список.
