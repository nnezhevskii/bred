# Архитектура parser и analyzer

Срез `09472ab`. Отправная точка — стоимость следующего изменения синтаксиса и следующего правила типов. Конкретные воспроизведения находятся в [parser review](PARSER_REVIEW.md) и [analyzer review](ANALYZER_REVIEW.md).

## Parser: что масштабируется удачно

`ParserFactory` соединяет небольшие парсеры конструкций, ленивые зависимости разрешают естественную рекурсию block → statement → expression → when → block. Приоритеты выражений видны прямо в последовательности функций recursive descent. Для новой независимой инструкции есть понятное место маршрутизации. Такую организацию можно сохранять, пока ветки разбора локальны и возвращают AST или ASTError. ## Parser: где нужны границы

| Решение | Цена при изменении | Первая граница рефакторинга |
|---|---|---|
| For разворачивается во время разбора | Теряется исходная конструкция, служебное имя захватывает пользовательское, analyzer отключает часть flow checks. Добавление continue потребует учесть место инкремента. | Сохранить For с границами и исходным телом, понижать после проверки привязок. Начать с сохранения тела и теста имён. |
| FunctionParser добавляет синтетический return | Parser угадывает завершение тела по наличию top-level Return; downstream обязан помнить explicit=false. Для if с возвратом в обеих ветках добавляется лишний хвост. | Вынести нормализацию завершения в этап после анализа путей. На первом шаге явно зафиксировать, кто вправе игнорировать синтетический узел. |
| TypeRef и разрешённые типы занимают одни поля TypeSign | Одна сигнатура метода допускает дерево нескольких стадий, прямой вызов следующего прохода может быть преждевременным. | Объект результата стадии с деревом и контекстом; сначала проверять согласованность границы. Полное дублирование всех AST-классов для этого не требуется. |
| ContextCollector и TemplateInstantiator лежат в parser | В модуле синтаксиса появляются поиск перегрузок, подстановка типов и выбор instance. Правила типов приходится воспроизводить до analyzer. | Первым вынести общее чистое правило типа бинарного оператора, доступное обеим стадиям без цикла зависимостей. Отдельный модуль оправдан при устойчивом контракте семантической подготовки. |
| Суффиксы call/index/field выбираются единожды после identifier | Для fighters[i].score нужны изменения формы AST и цикла разбора суффиксов. ## Analyzer: повторение правил уже даёт наблюдаемые пробелы

Объявления scalar, array и global по отдельности выполняют проверки имён, initializer и типов. Параметры напрямую пишутся в Scope. Из-за этого обычный scalar обнаруживает повтор, а массив и второй параметр перезаписывают запись. Общая операция регистрации привязки с результатом «новая / затенила / повтор в этой области» имеет конкретную пользу. Обход AST и формулировки диагностик могут остаться в своих ветках. [Объявления и Scope](../analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt)

**Области видимости и поток управления сцеплены.** Scope хранит родителя, переменные, функции, состояние initializer, expectedReturnType, общую таблицу типов и флаг проверки потока. `withControlFlowChecks(false)` создаёт новую оболочку с теми же изменяемыми картами, а внутренние области наследуют флаг. В результате одна локальная потребность развёрнутого for меняет проверку всех его вложенных блоков. Полезно передавать контекст функции и результаты анализа путей отдельно от таблицы видимых имён. Первая проверяемая граница — одинаковая диагностика пользовательского unreachable в for и while.

**Flow-анализ повторяет обход вложенных блоков.** analyzeBlockFlow рекурсивно просматривает дочерние конструкции, а visit затем входит в те же блоки и снова запускает их flow-анализ. У глубоко вложенной цепочки блоков объём повторной работы может расти квадратично. Это аналитическая оценка по коду, измерения не выполнялись. При следующей работе над полным when выгодно возвращать из анализа блока одно заключение о возможных выходах и использовать его у родителя. Это также объединит критерии полноты и завершения функции.

**Таблица типов не выражает завершённость проверки.** Массивный initializer записывает тип элемента, пустой не записывает ничего. При этом другие ветки используют !!. Нужно явно различать результат типизации обычного выражения, специальный initializer с ожидаемым типом и ошибку. Первый небольшой контракт — visit initializer либо возвращает проверенные сведения, либо Left, без неявного отсутствия типа, которое соседняя ветка считает невозможным.

**Контракт результата анализа должен расти вслед за решениями.** В SemanticAnalysisResult есть warnings и IdentityHashMap типов. Добавление выбранных привязок, сигнатур и вариантов when снимает повторный поиск в lowering. Начать с одного вида ссылки и передавать результат вместе с точным экземпляром дерева. Копирование дерева после построения identity-таблиц потребует повторного анализа или явного переноса фактов.

## Что пока можно сохранить

TypeValidator с чистыми правилами операторов удобен для предметных тестов. Раздельный SemanticDiagnosticFormatter позволяет менять сообщения независимо от логики проверки. Fail-fast внутри блока с накоплением ошибок между функциями — понятный компромисс, пока документирован порядок диагностик. Kotlin-файлы в src/main/java и повтор `org.nnezh` в отдельных package стоит убирать при касании соответствующих файлов; они дают меньший эффект, чем единая регистрация привязок и явное происхождение for.

**Последовательность:** регистрация параметров и массивов → результат типизации initializer → flow исходного тела for → факты о выбранной привязке → общие правила типов со специализатором. Каждый шаг имеет самостоятельный регрессионный пример.
