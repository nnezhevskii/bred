Срез `09472ab`. Решения ниже оценены по тому, сколько кода нужно понимать, чтобы добавить операцию, поменять представление значения или подключить нативную проверку. Наблюдаемые последствия вынесены в [ревизию backend](C_BACKEND_REVIEW.md); примеры на стороне потребителя — в [разбор C](GENERATED_C_REVIEW.md).

Эти границы стоит сохранить. ## Где изменение уже оправдано

### 1. Рендеринг уничтожает информацию об операнде до выбора операции

В `ASSIGN` источник сначала превращается в текст через `asRightValue()`. Решение «создать строку из литерала» принимается позже, только по типу destination. Переменная `src` и литерал `"src"` на этом этапе представлены одним текстом. В результате программа фактически печатает имя переменной.

**Граница рефакторинга:** выбирать способ генерации по исходному `Operand` и ожидаемому типу, а текст получать в последнем шаге. Начать с пары StringConst / Variable и теста на обе формы. Это полезнее общего добавления проверок типов во все opcode. [ASSIGN](../c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt) · [Операнды](../common/src/main/kotlin/org/nnezh/ICGenerator/Operand.kt)

### 2. Нормализация входа перемешана с печатью

`compile` отдельно собирает варианты сумм, структуры, глобальные массивы, заголовки функций. Далее курсор ещё раз разбирает заголовок и параметры каждой функции; `parseFunction` просматривает тело вперёд для локальных объявлений. `CALL` читает назад, а конец функции определяется следующим заголовком или концом всего списка. Добавление позиции исходника между `PARAM` и `CALL` уже потребовало бы знания физического соседства инструкций.

**Первая граница:** внутри модуля собрать явную функцию с заголовком, параметрами и телом и передавать её рендереру целиком. Тело владеет обеими фигурными скобками. Начать с пустой программы, двух функций подряд и функции без параметров. Проверку порядка метаданных сделать в месте чтения, где доступен исходный индекс. Когда TAC начнёт передавать функции объектами, этот слой можно сократить. [compile, parseFunction, Context](../c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt) · [Предложения для TAC](TAC_ARCHITECTURE.md)

### 3. Сведения о вводимых переменных восстанавливаются по исключениям

Для объявления локальной переменной `parseFunction` читает `destination` и поддерживает список opcode, которые надо пропустить. Например, `PARAM` только читает значение, `STORE_FIELD` изменяет поле, `ALLOC` задаёт место хранения. Новая инструкция с `destination` может потребовать изменения незаметного для автора второго участка кода. Группировка по типу и тексту имени также теряет идентичность привязок при затенении.

**Первый шаг:** явно описать операции, вводящие локальное хранение, и передать функции набор локальных привязок с типами. Можно начать с единственной таблицы ролей внутри backend. Случаи для проверки — изменение поля параметра, передача массива и две разные исходные привязки с одним именем. Надёжное различение привязок требует участия TAC; восстановить потерянную идентичность по C-строке нельзя. [parseFunction](../c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt) · [Модель инструкций](../common/src/main/kotlin/org/nnezh/ICGenerator/LLTACInstruction.kt)

### 4. У представления типов и имён нет одного владельца

`typeToStringInInitialization` и `typeToStringInArguments` повторяют скалярные правила, но массив для аргумента превращается в указатель; то же отображение используется для результата. `isProductType` считает продуктом всякий resolved, non-primitive, non-array тип. Названия для C проходят разными путями: пользовательские имена вставляются напрямую, типы используют `toManglePart`, служебные `size` и `arg` фиксированы, поля суммы уже склеены в TAC. Изменение одного способа именования легко разъединит объявление и ссылку.

**Развести два решения.** В одном месте задавать представление Bred-типа для поля, локального хранения, параметра и результата. Отдельно отображать идентичность объявления в C-имя, учитывая ключевые слова, символы runtime и служебные имена. Начать с `switch` в параметре и зависимости `Outer → Inner`. Для структур по значению требуется порядок полных определений. Одни предварительные декларации такую зависимость не закрывают. [Сигнатуры и структуры](../c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt)

### 5. Соглашения с runtime и точкой входа скрыты в специальных ветках

Имя `main` меняет сигнатуру и добавляет `init_runtime()`. `ADD` над строкой означает `concat`, конструктор распознаётся по имени и типу destination, обычное сравнение структур превращается в C-оператор. Один opcode обслуживает разные операции с разными требованиями. При добавлении нового типа автору приходится одновременно помнить об анализаторе, именах C-функций и их фактическом наличии в `runtime.c`.

**Узкая миграция:** ввести C-обёртку точки входа с оговорённым кодом выхода, а пользовательскую функцию генерировать обычным путём. Для строк зафиксировать три операции — создать литерал, скопировать значение, склеить. Для каждой указать C-представление или символ runtime. Расширять контракт при добавлении операций. Проверять extern хотя бы одним тестом на компоновку реального runtime. [Список extern](../common/src/main/kotlin/org/nnezh/bred/common/ExternalFunctionSpecs.kt) · [Runtime](../runtime.c)

## Пока работает, но важен момент пересмотра

| Решение | Цена при росте | Когда брать |
|---|---|---|
| `firstFunctionWasProceeded` и `sumDefinitions` — поля объекта | Последовательные вызовы сбрасывают состояние, это покрыто тестом. Два одновременных вызова на одном объекте могут перезаписать сведения друг друга. Корневой компилятор хранит экземпляр transpiler. Это риск по коду, конкурентный сбой не воспроизводился. | При выделении тела функции убрать флаг, таблицу сумм сделать локальной для одного `compile`. Проверить повторное использование с двумя разными программами. |
| Несколько проходов по инструкциям | Несколько линейных проходов — разумная цена. Дублированное распознавание одних и тех же конструкций делает изменения дорогими раньше, чем время исполнения. | Объединять разбор заголовков ради одного контракта. Производительность оценивать на измерении большой программы. |
| Опциональные операнды и приведения внутри рендера | `parseInstruction` добавляет индекс к ошибкам, но сбор метаданных и заголовков идёт отдельно. `catch(Throwable)` может представить внутренний сбой как ошибку TAC. | При следующем изменении формата разделить ошибку структуры входа, неподдержанное представление Bred и внутреннюю ошибку backend. Тест — оборванная структура и вызов без группы PARAM. |
| Строки C как результат Kotlin API | Список строк удобен для маленьких тестов и публичного API. Сложнее отследить, откуда взялась строка после добавления runtime и прототипов. | При работе над диагностикой сохранять соответствие диапазона строк C функции и индексу TAC. Полное дерево синтаксиса C ради этого не требуется. |
| Проверки точного текста | Хорошо ловят сломанное экранирование, порядок прототипов и форму конструктора. Тест минимального main закрепляет также `return;` в `int main`. | Разделить цель теста: на Kotlin проверять решение рендерера, через MSVC — допустимость C, запуском — результат программы. |

**Реалистичный порядок:** сначала исправить `ASSIGN` по виду источника. Затем сделать функцию единицей печати и вынести обёртку main.
