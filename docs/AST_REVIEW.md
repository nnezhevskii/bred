# Форма АСД: что сохраняется и что теряется

Срез `09472ab`. Parser создаёт синтаксические data class. Resolver и TemplateInstantiator строят преобразованные экземпляры той же модели. Analyzer добавляет таблицу типов с ключами по идентичности узлов и меняет флаг конструктора у вызова. Поэтому для работы с «семантическим деревом» фактически нужны и конкретный AST, и внешние факты о нём. [Модель](../parser/src/main/kotlin/org/nnezh/bred/ast/AST.kt) · [Выражения](../parser/src/main/kotlin/org/nnezh/bred/ast/ASTNode.kt)

## Проверенные примеры формы

| Написано | Получено в AST | Последствие |
|---|---|---|
| `return 2147483648` | `IntLiteral(value=-2147483648)` | Исходное значение уже невозможно проверить по узлу. |
| `val a: Int[4294967296]` | `ArrayDeclaration(size=0)` | Анализатор видит другой размер. |
| `for (i in 0 to 3) { … }` | `For(desugaredContent=Block(init i, init _right_borderi, While(...)))` | Исходное тело и синтетический инкремент лежат в одном преобразованном дереве. |
| `fun f() {}` | В теле один `Return(null, explicit=false)` | Пустая исходная функция уже нормализована parser. |
| `fun f(Unit: Int): Int { return Unit }` | `Return(null, explicit=true)` | Имя параметра теряет значение в специальном синтаксисе return. Это поведение описано в грамматике. |
| `type P(x: Int y: Long)` | Два поля продукта | Неверное разделение полей не отражено ошибкой. |

## Источники трудностей в самой модели

**Позиции хранятся неравномерно.** VariableExpression сохраняет Token, операторы — LocatedOperator. Имена функций, полей, объявлений и вызовов сохраняются строками, литерал — только значением. Formatter восстанавливает позицию по доступным дочерним узлам. Ошибке повторного типа нужны места обоих объявлений; после текущего разбора их уже нет. Ввести span объявления и span выражения, включая идентификатор, плюс происхождение синтетического узла. Начать с сообщения о повторе параметра. [Formatter](../analyzer/src/main/java/org/nnezh/SemanticDiagnosticFormatter.kt)

**Допустимы комбинации, которых обычный parser не создаёт.** DeclareGlobalVariable имеет nullable type и expression, размер и флаг мутабельности. Assignment допускает любой Expression как lValue, хотя модель содержит LeftValue. CallFunctionStatement тоже принимает любой Expression. Прямой клиент может создать ArrayDeclaration с обычным выражением, а analyzer приводит initializer к ArrayInitialization. Уточнить публичный контракт конструкторов. Небольшое улучшение — отдельная форма initializer в объявлении массива и вход анализатора уровня ProgramRoot с проверенными типами. При этом семантическая проверка assignability остаётся нужна для предметного сообщения пользователю.

**Мутация семантического флага влияет на data class.** `FunctionCallExpressionASTNode.isConstructorCalling` по умолчанию true и входит в primary constructor. Изменение analyzer участвует в сгенерированных equals/hashCode. IdentityHashMap текущей таблицы устойчив к такой мутации, но обычный HashMap или Set с узлами получит изменяемый ключ. Клонировщик переносит флаг в копию, что также может перенести устаревшее решение при изменившемся контексте. Хранить выбранную цель в фактах анализа, привязанных к конкретной версии дерева. [Клонирование](../parser/src/main/kotlin/org/nnezh/bred/ast/AstCloner.kt)

**Одинаковая форма типов имеет несколько толкований.** `Int[]` в аргументе представлен `type=Int, isArray=true`, а `Array<Int>` — типом с аргументом. ArrayDeclaration хранит указанный тип и размер отдельно. Потребители вызывают свои scopeType/asArrayType/arrayElementType. На границе resolver полезна одна каноническая форма параметра; исходное написание можно сохранять отдельно для сообщения.

**Образец when остаётся выражением.** `Just(value)` в condition — FunctionCall, хотя value объявляется этой веткой. Обычное посещение выражения до учёта контекста могло бы проверить его как чтение неизвестной переменной. Сохранить синтаксическую форму возможно, но после анализа полезен явный результат «вариант + привязки» для следующей стадии. Else как null остаётся компактным представлением, пока все потребители трактуют его одинаково.

**ProgramRoot разделяет объявления по спискам.** Глобальный порядок функций, типов и переменных не сохраняется. Для нынешних проходов с предварительным сбором это удобно. При добавлении import, атрибутов либо диагностик в порядке исходника понадобится общий список объявлений или сохранённые позиции. Сейчас не стоит возвращать order только ради новой структуры данных. Поле functions — MutableList, остальные списки объявлены List; нужно явно обозначить владельца преобразований, чтобы таблицы анализа не пережили изменение списка.

## Удобный контракт после анализа

Одна программа должна передаваться дальше вместе с таблицами, построенными именно для неё: тип выражения, выбранная привязка, цель вызова и проверенный образец. Перед созданием этой пары завершаются преобразования, меняющие идентичность узлов. Для следующего изменения выбрать один новый факт — например привязку ссылки на параметр — и проверить, что TAC не ищет её заново по строке. Полный переход на отдельную модель typed AST можно оценить после этого эксперимента.

Для первой сессии — напечатать дерево for с пользовательским `_right_borderi`, отметить четыре исходных и синтетических места, затем написать проверку происхождения границы. Это покажет, какую информацию действительно нужно добавить.
