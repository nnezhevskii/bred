## Что сейчас работает

На JDK 25 команда `.\gradlew.bat test --continue --rerun-tasks` выполнила 387 тестов. Прошли 384, упали 3, пропущено 0. По модулям (прошло / всего) — lexer 48/48, parser 103/105, analyzer 152/152, tac 50/50, c-backend 17/17, корень 14/15. В common нет отдельной тестовой задачи с тестами. Первая задача ниже объясняет все три падения.

Это результат запуска JVM-тестов. Корневые тесты проверяют строки C и используют подставной C-компилятор при тестировании сборщика. Нативный прогон через MSVC в ревизию не входил. Для остальных находок основание — чтение указанных веток реализации. Предложенные проверки описывают будущие регрессии.

### G-74. Тесты радара читают изменяемое CLI-демо

Два теста парсера и один корневой упали. Все три читают `examples/3ac.bred`, где теперь объявлен `Shape`. Семантический тест с именем радара зелёный, но тоже читает фигуры.

**Проверка и следующий шаг.** Выделить стабильную фикстуру для радара. Полный текст с `Metrics` и `FleetAudit` есть в `git show e90d4f4:examples/3ac.bred`. У короткой TAC-версии этих типов нет. Проверить подключение `Maybe` из stdlib в корневом API и все четыре потребителя.

[Парсер](../parser/src/test/kotlin/org/nnezh/bred/ast/Example3acParserTest.kt), [семантика](../analyzer/src/test/kotlin/org/nnezh/Example3acSemanticTest.kt), [корневой API](../src/test/kotlin/org/nnezh/root/BredCompilationFactoryTest.kt)

### G-75. Сборщик может удалить чужой C-файл при раннем выходе

`build` вычисляет имя C-файла рядом с exe. Даже если проверка `vcvars64.bat` сразу вернула ошибку, `finally` вызывает `deleteIfExists` при стандартном `keepIntermediateC=false`. Если сборка дошла до записи, одноимённый файл уже перезаписан.

**Проверка и следующий шаг.** В тесте с `@TempDir` положить маркер в существующий `demo.c`, передать отсутствующий vcvars и запросить `demo.exe`. Проверить сохранность маркера. Для обычной сборки определить владение промежуточным файлом и проверить успешный путь.

[CExecutableBuilder.build](../src/main/kotlin/org/nnezh/CExecutableBuilder.kt)

### G-76. CLI игнорирует keep-c

`main` разбирает третий аргумент, но передаёт сборщику константу `true`. Поэтому `false` и отсутствие аргумента сохраняют C-файл вопреки README.

**Проверка и следующий шаг.** После G-75 передать разобранное значение и проверить CLI для отсутствующего аргумента, `false` и `true`. Тесты прямого вызова builder этот путь обходят.

[Main](../src/main/kotlin/org/nnezh/Main.kt), [контракт CLI](../README.md)

### G-77. Код возврата CLI зависит от текста сообщения

При отсутствующем runtime builder возвращает `Runtime C file does not exist`. Ни одна из трёх проверок подстрок в CLI его не ловит. И наоборот, успешный путь с каталогом `errors` совпадает с `error`.

**Проверка и следующий шаг.** Передавать успех или ошибку отдельно от текста. Проверить оба случая, включая отсутствие runtime при доступном vcvars.

[Main](../src/main/kotlin/org/nnezh/Main.kt), [builder](../src/main/kotlin/org/nnezh/CExecutableBuilder.kt)

### G-78. Int-литерал может тихо поменять значение

Лексер принимает значение в диапазоне Long, затем парсер вызывает `toInt()`. Положительное `2147483648` превращается в `-2147483648`. Аналогичное сужение есть у размера массива.

**Проверка и следующий шаг.** Проверить границу Int, следующее значение, суффикс L и большой размер массива. Отдельно определить разбор `-2147483648`, поскольку минус является оператором.

[Лексер](../lexer/src/main/kotlin/org/nnezh/lexer/Lexer.kt), [выражения](../parser/src/main/kotlin/org/nnezh/bred/ast/AbstractSyntaxTreeExpressionParser.kt), [объявления](../parser/src/main/kotlin/org/nnezh/bred/ast/VariableInitializationParser.kt)

### G-79. Глобальный скаляр пропадает между AST и TAC

Для `val limit: Int = 7` узел глобальной переменной проходит семантику, но генератор выдаёт хранилище только внутри `node.size?.let`. Использование `limit` в функции теряет определение и начальное значение. Это отдельный случай от G-61 про элементы массива.

**Проверка и следующий шаг.** Проверить чтение `limit` из функции вплоть до результата 7. Минимальный контракт для первого изменения — глобальный Int с литералом.

[LLTACGenerator](../tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt), [описание ограничения](ast_to_3ac_generation.md)

### G-80. Затенение локальной переменной теряется в C

Анализатор разрешает внутренний `val n` с предупреждением. TAC сохраняет исходное имя и обходит блок как список. Backend собирает объявления по типу и имени на всю функцию. При одинаковых типах две привязки получают одну C-переменную.

**Проверка и следующий шаг.** В семантический пример с внешним `n = 1` и внутренним `n = 2` добавить чтение после блока. Ожидать 1. Затем проверить одноимённые переменные разных типов. Рассмотреть отдельный идентификатор каждой привязки.

[Тест затенения](../analyzer/src/test/kotlin/org/nnezh/SemanticAnalyzerTest.kt), [CTranspile.parseFunction](../c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt)

### G-81. Сравнения строк доходят до недопустимой операции C

`TypeValidator` разрешает сравнивать две строки на равенство и порядок. `String` представлен C-структурой, а `generateSimpleOperation` печатает обычные `==` и `<`. То же расхождение есть для равенства продуктовых значений.

**Проверка и следующий шаг.** Проверить две отдельно созданные равные строки и две разные. Для продуктов явно определить семантику равенства. Закрепить контракт между анализатором и backend тестом с компиляцией C.

[TypeValidator](../analyzer/src/main/java/org/nnezh/TypeValidator.kt), [CTranspile](../c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt), [правила операторов](semantic_analysis_draft.md)

### G-82. Длина строкового литерала зависит от пути генерации

Грамматика допускает `\0`. Backend пропускает декодированный NUL в текст C и использует `strlen` для локального литерала. Для глобального массива строк длина берётся из Kotlin `String.length` в единицах UTF-16, а `concat` копирует байты.

**Проверка и следующий шаг.** Проверить `"a\0b"` и не-ASCII строку в локальном и глобальном вариантах. Задать кодировку C-литералов, сверить байтовую длину и содержимое после конкатенации.

[Литералы](grammar.md), [escapeCString / renderGlobalInitializer](../c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt), [runtime](../runtime.c)

### G-83. readInt зацикливается в конце ввода

После неудачного `scanf` цикл читает до перевода строки. На пустом stdin или на последней некорректной строке без перевода строки `getchar()` продолжает возвращать EOF.

**Проверка и следующий шаг.** Тест с закрытым stdin и таймаутом. Для пустого ввода и `abc` без перевода строки функция должна закончить работу. Зафиксировать возвращаемое значение в контракте runtime.

[readInt](../runtime.c)

### G-84. Демо вычисляет площадь и возвращает константу

Каждая ветка `square` записывает результат в `value`. Единственный `return 0.0` отбрасывает его. Это видно на прямоугольнике 2 × 4, где должно получиться 8.

**Проверка и следующий шаг.** Вернуть вычисленное значение. Проверить прямоугольник и квадрат, у которых результат точный. У демонстрации в конце есть чтение числа.

[Демо фигур](../examples/3ac.bred)

### G-86. Пробелы внутри строк исчезают при сравнении снимков

`LLTAGSnapshotTester` удаляет все обычные пробелы у ожидаемого и фактического TAC. В снимке `isPositive` изменения `number: ` → `number:` пройдут незамеченными.

### G-87. Перегрузки обычных функций могут получить одно имя в C

Анализатор выбирает перегрузку по типам. В TAC `mangleFunctionName(FunctionDeclAstNode)` возвращает `function.name`. Тест `user function calls use mangled target name` получает TAC, но ничего не утверждает о цели вызова.

**Проверка и следующий шаг.** Взять две обычные перегрузки с аргументами Int и Long. Проверить, что определения различаются в C и оба вызова выбирают нужное тело. У generic-специализаций своё формирование имени.

### G-88. Две точки входа повторяют подготовку программы

`compileChecked` и `TACCompilerImpl.compile` повторяют сбор контекста, разрешение типов, инстанцирование, повторное разрешение и анализ. У корневого API добавляется stdlib и другой контракт ошибок. Изменение порядка фаз приходится переносить вручную.

**Проверка и следующий шаг.** Перед выделением общего прохода проверить одну программу на обеих точках входа, отдельно зафиксировать различия в stdlib и диагностике. Рефакторить при следующем изменении этих фаз.

[Root compiler](../src/main/kotlin/org/nnezh/BredCompilationFactory.kt), [TACCompiler](../tac/src/main/kotlin/org/nnezh/compiler/TACCompiler.kt)
