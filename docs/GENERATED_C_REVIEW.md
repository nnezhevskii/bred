# Каким получается C после компиляции Bred

Срез `09472ab`, MSVC x64 19.51.36252. Предмет этого документа — код, который увидит C-компилятор, и последствия для запуска. В [ревизии backend](C_BACKEND_REVIEW.md) есть входы и результаты проверок; в [архитектурном разборе](C_BACKEND_ARCHITECTURE.md) — места для изменений в Kotlin. Ниже отдельно отмечено, что наблюдалось нативно и что следует из чтения текста.

## 1. Что именно компилируется

`CTranspile.compile` возвращает определения типов и глобальных массивов, прототипы и тела. Корневой `CExecutableBuilder` приписывает перед ними весь `runtime.c`. В результате `String`, `bool`, `concat` и `init_runtime` видны сгенерированной части; она сама по себе не является автономным C-файлом. Для корректного сравнения в проверках использован тот же порядок. Демо проекта действительно компилируется с этим runtime. [Builder](../src/main/kotlin/org/nnezh/CExecutableBuilder.kt) · [Runtime](../runtime.c)

**Положительный контроль.** `fun f(x: Int): Int { return x + 1 }` превратился в `int f(int x)` с локальной переменной для единицы и отдельной переменной для суммы. Программа, печатающая `f(7)`, дала `8` и код 0. Такой код избыточен по числу временных, зато легко сопоставляется с TAC. В штатном builder указан `/Od`; здесь не измерялась скорость программы и нет основания оптимизировать временные первыми.

## 2. Компилируемый C с неверным результатом

**Копирование строки.** Настоящий фрагмент исполняемой программы:

```c
String src, dst;
src = create_string("hello", strlen("hello"));
dst = create_string("src", strlen("src"));
println(dst);
```

Программа вывела `src`; вариант с копией из параметра вывел `x`. Присваивание структуры `dst = src;` при текущем runtime копирует указатель и длину. Данные уже лежат в пуле до завершения программы, так что создавать новый литерал из имени локальной переменной здесь не нужно. Нативный тест должен сравнивать stdout, поскольку типы в этом C полностью согласованы.

**Байты строки.** Для глобального `"é"` фактический инициализатор использует длину 1. После добавления `"!"` получены байты `C3 21` вместо полного UTF-8 символа и `21`. На другой настройке кодировки представление литерала может отличаться; ошибочен сам расчёт байтовой длины по Kotlin `String.length`. Один вариант реализации — выдавать однозначно закодированные байты и брать `sizeof(литерал) - 1`. Общий контракт нужен и для локальных строк, где сейчас используется `strlen`. Грамматика поддерживает `\0`; `strlen` остановится на первом нулевом байте, а `println` с `%s` тоже завершит вывод раньше поля `length`. Последний случай установлен по коду. [Рендеринг литералов](../c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt) · [Операции со String](../runtime.c)

## 3. Время жизни, массивы и инициализация

- **Высокий приоритет.** В фактическом выводе для `tokens(): Array<Int>` объявлено `int a[1];` и выполнено `return a;` из функции с результатом `int*`. Хранение заканчивается с возвратом. Это дефект даже при успешной трансляции. Проверка ограничилась инспекцией C. Варианты контракта — явный выходной буфер, массив с определённым владельцем либо запрет выхода локальной привязки из функции. Сначала зафиксировать, какие возвраты разрешает язык.
- **Размеры.** `Array<Int>` в параметре представлен как `int*`; длина не передаётся автоматически. Загрузки и записи имеют форму `a[i]`. Для обращения с проверкой границ потребуется договорённость, откуда получить длину. Большие локальные статические массивы занимают место в кадре вызова; для них стоит определить допустимый размер. Нативный результат для нулевого размера уже конкретен — MSVC отверг `int a[0];`.
- **Начальные значения.** Глобальный массив без инициализатора в C получает нулевую инициализацию. Локальное `int a[n];` с константным положительным n и без инициализатора не задаёт значения элементов. Если Bred обещает начальное значение, его нужно выдать явно. Если язык требует записи до чтения, это проверка frontend. Приёмочный тест должен опираться на выбранное правило, а не на случайный вывод одного запуска.
- **Строковый пул.** Runtime выделяет 16 МиБ, `create_string` и `concat` продвигают общий offset, а после исчерпания вызывают `exit(1)`. Конкатенация в цикле удерживает все промежуточные строки до завершения. Это ограничение времени жизни и общей ёмкости runtime; замеров производительности здесь не было. [Runtime](../runtime.c) · [Представление массивов](type_system.md)

## 4. Имена, сигнатуры и порядок объявлений

| Полученный C | Что означает для автора программы |
|---|---|
| `typedef struct Outer { Inner inner; } Outer;` перед определением `Inner` | MSVC отверг поле по значению. Полное определение вложенного типа должно предшествовать внешнему. Для функций предварительных прототипов обычно хватает, для такого поля — нет. |
| `typedef struct Empty { } Empty;` | Пустой продукт допускает Bred, MSVC отказал с C2016. Если выбрать служебный байт, проверить также создание пустого значения. |
| `int f(int switch);` | Допустимый идентификатор Bred стал ключевым словом C. Собственный префикс плюс стабильное отображение имён нужны и для взаимодействия с обычными символами runtime. |
| `int main(int size, char** arg)` и `int size;` в теле | MSVC сообщил повторное объявление. Отдельный параметр Bred `user` вообще исчез из C-сигнатуры, хотя тело продолжает его читать. |
| `return;` в `int main(...)` | Так завершились проверенные работоспособные демо; у запущенных примеров зафиксирован код 0. Генератор при этом не выражает значение результата в исходном C. Сделать успешное завершение явным через `return 0;` в обёртке. |
| `void f();` для функции без аргументов | В C-диалектах до C23 объявление с пустыми скобками не задаёт типизированный список параметров. Если целью остаётся такой режим, `void f(void);` лучше выражает контракт. Это замечание по интерфейсу, нативного сбоя в контроле не наблюдалось. |

## 5. Арифметика, равенство и поток управления

- `var1=a==b;` для двух `String` не проходит MSVC. Та же форма требует отдельного решения для продуктовых и суммарных структур. Указатели массивов в C сравниваются по адресу; если язык обещает поэлементное равенство, нужна другая реализация. Для каждой категории типа определить операции сравнения и проверить две равные по содержимому, но отдельно созданные строки.
- `+`, `-`, `*`, `/` и `%` для знаковых чисел выдаются как обычные C-операторы. Переполнение знаковых целых и деление на ноль требуют явного контракта языка. `/Od` не задаёт этот контракт. Это наблюдение по реализации. Если Bred выбирает проверяемую арифметику, нужен один общий механизм проверки; для арифметики по модулю — гарантированное представление результата на целевой платформе.
- `&&` и `||` в файле C выглядят как операторы с коротким замыканием. Их операнды уже вычислены предшествующими инструкциями TAC. Поэтому вызов с побочным эффектом справа может выполниться до самого C-оператора. Это решение на стороне lowering, G-89; замена текста одной строки backend не изменит порядок эффектов.
- У `when` в C остаются метки, сравнения тегов и переходы. Для небольшого числа ветвей это прозрачный результат. В сгенерированном представлении суммы хранятся поля всех вариантов одновременно; при крупных payload это увеличивает размер объектов и стоимость передачи по значению. Перед переходом на union измерить размеры реальных типов и проверить согласованное создание и чтение вариантов. [Правила opcodes](3ac_to_c_generation.md) · [Ревизия TAC](TAC_REVIEW.md)

## 6. Практический набор проверок для сгенерированных программ

1. **Значение.** В публичном API со stdlib собрать программу из раздела 2, запустить, ожидать stdout `hello` и успешный статус процесса. Отдельно повторить с копией из параметра.
2. **Байтовая точность.** Под выбранной кодировкой проверить одинаковый вывод локального и глобального `"é" + "!"`. Для встроенного NUL проверить длину, содержимое и отдельно документированное поведение вывода.
3. **Компиляция.** Для forward-типа, пустого продукта, нулевого массива и C-ключевого слова проверять либо успешную нативную сборку, либо предметную диагностику Bred до MSVC. Для файлов без entry point собирать объект без линковки.
4. **Время жизни.** Проверять диагностику возврата локального массива или выбранное владеющее представление. Положительные проверки для возврата массива из аргумента и из глобального хранения зависят от принятого контракта.
5. **Полный путь.** Сохранить существующее демо как smoke-тест на stdlib, runtime, компоновку и запуск. Для проверки численного результата выбрать маленькую программу с известным ответом: текущий пример фигур сам возвращает константу. Для отдельного теста со stdin дать число, поскольку демо заканчивается чтением ввода. [Исходник демо](../examples/3ac.bred)
