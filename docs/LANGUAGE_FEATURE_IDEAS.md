# Какие фичи я бы добавила в Bred

Я бы развивала Bred вокруг того, что у него уже получается: типы-суммы описывают варианты данных, продукты дают полям имена, а typeclass позволяют писать алгоритмы поверх разных типов. Самые интересные фичи здесь — те, с которыми небольшая программа становится одновременно короче и точнее.

Все фрагменты ниже показывают **предлагаемый синтаксис**. Имена вроде `parseInt`, `toLong` и `Eq` входят в соответствующее предложение. Где идея уже обсуждалась, указан её ID из [TODO](TODO.md). Действующий синтаксис описан в [грамматике](grammar.md).

## 1. Возвращать значение из when

```bred
fun area(shape: Shape): Double {
    return when (shape) {
        Circle(r) -> r * r * 3.1417
        Rectangle(w, h) -> w * h
        Square(side) -> side * side
    }
}
```

**Зачем.** В сегодняшнем примере фигур каждая ветка правильно записывает площадь в `value`, а после `when` функция случайно возвращает `0.0`. В этой записи результат выбранной ветки сразу становится результатом функции. При добавлении `Triangle` компилятор может показать все места, где ещё нужна формула. [Текущий пример](../examples/3ac.bred)

**Первая версия.** Одна ветка — одно выражение. Для суммы проверять полноту, для произвольного значения требовать `else`. Типы результатов всех веток должны совпадать. Здесь уже есть готовая основа — разбор вариантов, привязка payload и проверка полноты. G-71.

## 2. Сцеплять индексы и поля в одном выражении

```bred
fun riskAt(fighters: Array<Fighter>, i: Int): Int {
    return fighters[i].risk
}
```

**Зачем.** В `totalScore` и `maxRisk` приходится заводить `val fighter: Fighter = fighters[i]` только ради чтения одного поля. Хочется, чтобы к любому выражению подходящего типа можно было применить следующий шаг: `fighters[i].risk`, `makeTeam().captain.name`, `team.scores[i]`. [Пример с бойцами](../examples/difficult.bred)

**Первая версия.** Только чтение. В `fighters[nextIndex()].risk` индекс вычисляется ровно один раз. Для присваивания через такую цепочку отдельно потребуется определить, в каких местах находится изменяемое хранилище. G-12.

## 3. Дать массиву длину и обход по элементам

```bred
fun totalScore(fighters: Array<Fighter>): Int {
    var total: Int = 0
    for (fighter in fighters) {
        total = total + fighter.score
    }
    return total
}
```

**Зачем.** У `sortByRank`, `renderArray` и `totalScore` рядом с массивом путешествует `size`. Вызов с правильным массивом и чужим размером выглядит совершенно законно. Для суммирования индекс вообще не нужен; сортировке останется доступен `items.size` и привычный `for (i in 0 to items.size)`. [Сигнатуры в примере](../examples/difficult.bred)

**Первая версия.** Статический массив знает размер из объявления, параметр массива получает его вместе с адресом. Переменная цикла — неизменяемое значение элемента. Пустой массив выполняет ноль итераций. Эта фича меняет представление параметров в C и заслуживает отдельной задачи.

## 4. Именованные аргументы у конструкторов продуктов

```bred
type Limits(warnMs: Int, stopMs: Int, retries: Int)

val api: Limits = Limits(
    retries = 3,
    warnMs = 150,
    stopMs = 500
)
```

**Зачем.** В `Fighter(name, baseSkill, hype, entropy, score, risk, active)` пять соседних чисел. Перестановка `score` и `risk` проходит проверку типов. Имена полей уже известны компилятору, а на месте создания объекта они объясняют, что означает каждое число. [Реальный конструктор](../examples/difficult.bred)

**Первая версия.** Разрешить целиком именованный вызов конструктора. Проверять неизвестное имя, пропуск и повтор поля. Выражения вычислять в порядке записи вызова, даже если поля объявлены в другом порядке. Такую фичу можно добавить отдельно от значений по умолчанию и именованных аргументов обычных функций.

## 5. Выводить тип локальной переменной по инициализатору

```bred
val label = "latency"
var retries = 3
val started = currentTimeMillis()
```

**Зачем.** В этих трёх строках типы однозначны: `String`, `Int` и `Long`. При просмотре алгоритма полезнее видеть, откуда взялось значение. Явная аннотация остаётся удобной для сигнатур и для проверки намерения автора.

**Первая версия.** Выводить тип только у локальных `val` и `var` с однозначным инициализатором. Тип `retries` фиксируется при объявлении. Для `[]` и неоднозначного `Nothing` запросить аннотацию с примером исправления. G-03, G-52, G-72.

## 6. Ввести номинальные типы для величин с одинаковым представлением

```bred
newtype Millis(value: Long)
newtype RetryCount(value: Int)

fun backoff(delay: Millis, retries: RetryCount): Millis {
    return Millis(delay.value * toLong(retries.value))
}
```

**Зачем.** Если задержка, отметка времени и идентификатор имеют тип `Long`, компилятор разрешает подменить одно другим. `Millis` и `RequestId` могли бы иметь одно машинное представление и разные типы. Явное `toLong` в примере заодно показывает место численного преобразования, которого сейчас не хватает в generic-примерах. G-70.

**Почему не начать просто с `type Millis(value: Long)`?** Для типобезопасности этого уже достаточно. Отличительное обещание `newtype` — представление базового значения на границе с C и отдельная идентичность при проверке Bred. Я бы сначала попробовала обычные одно-полевые продукты в живом примере и добавляла ключевое слово, только если действительно нужен такой ABI.

## 7. Интерполяция строк через typeclass

```bred
fun report(name: String, score: Int, elapsed: Long) {
    println("${name}: ${score} points in ${elapsed} ms")
}
```

**Зачем.** В `renderArray` содержимое отчёта теряется между `intToString`, конкатенациями и вызовами `show`. У Bred уже есть typeclass и пользовательские instance. Это позволяет одному и тому же синтаксису напечатать как число, так и `Fighter` с авторским форматированием. [renderArray и Printable](../examples/difficult.bred)

**Первая версия.** Определить стандартный контракт форматирования и экземпляры для примитивов. Вставки вычислять по одному разу слева направо. Отсутствующий экземпляр — ошибка на конкретной вставке. В нынешнем строковом пуле цепочка `concat` сохраняет все промежуточные строки, поэтому для длинного шаблона полезна одна сборка результата из фрагментов.

## 8. Result и ранний возврат ошибки через ?

```bred
fun parsePort(text: String): Result<Int, ParseError> {
    val port: Int = parseInt(text)?
    if (port < 1 || port > 65535) {
        return Err(PortOutOfRange(port))
    }
    return Ok(port)
}
```

**Зачем.** У строки `"oops"` и у числа `70000` разные причины отказа. Вызывающий код может вывести разные сообщения, а обычный путь читается как последовательность шагов. В проекте уже есть удачный прецедент — `Maybe<T>` объявлен на самом Bred. Так же можно сначала обкатать `Result<T, E>` как библиотечную сумму. [Стандартная библиотека](../stdlib.bred)

**Первая версия.** `parseInt` возвращает `Result<Int, ParseError>`. Оператор `?` извлекает значение из `Ok`; при `Err` сразу возвращает ту же ошибку из текущей функции. Для начала требовать одинаковый тип ошибки и внешний результат `Result`. Уточнить вывод типа второго варианта конструктора по ожидаемому типу `return`. Хорошая первая программа — парсер порта, проверенный на `"443"`, `"oops"` и `"70000"`.

## 9. Автоматически выводить экземпляры Eq для продуктов и сумм

```bred
type Point(x: Int, y: Int) derives Eq
type Marker = Missing | At(point: Point) derives Eq

val same: Boolean = equals(At(Point(2, 3)), At(Point(2, 3)))
```

**Зачем.** Это фича, которая особенно хорошо подходит именно Bred. Пользователь уже умеет писать instance, а компилятор знает поля продукта и варианты суммы. Для `Marker` естественное равенство сначала сравнит вариант, затем payload выбранного варианта. У добавленного завтра поля сравнение тоже появится; для поля без `Eq` компилятор сможет назвать препятствие. В C структуры Bred нельзя напрямую сравнить через `==`. G-81.

**Первая версия.** Генерировать обычный экземпляр `Eq` для конкретного типа без параметров, явно помеченного `derives Eq`; обнаруживать конфликт с ручным экземпляром. Отличный критерий — `Missing` отличается от `At(Point(0, 0))`, а две точки с одинаковыми координатами равны. Связать `==` с этим typeclass можно отдельным решением.

## 10. Обновлять отдельные поля неизменяемого продукта

```bred
type Strategy(name: String, budget: Long, risk: Int)

fun tighten(s: Strategy): Strategy {
    return s with { budget = s.budget / 2L }
}
```

**Зачем.** В модели с неизменяемыми продуктами часто нужен «тот же объект с другим бюджетом». Повторение конструктора заставляет перечислять несвязанные поля и создаёт риск перепутать соседние значения. `with` оставляет видимым ровно то, что меняется. Примером для проверки фичи могли бы стать модели `Strategy` и `Verdict`. [Модели в type_system_flex](../examples/type_system_flex.bred)

**Первая версия.** Работать с одним уровнем полей. Вычислить исходное значение один раз, скопировать продукт, проверить типы замен. Обновление возвращает новое значение; тест отдельно проверяет старый и новый `budget`. Для ссылочных полей отдельно описать, что копируется только само значение поля.

## Что я бы выбрала первым

**Для одной небольшой фичи — именованные аргументы конструкторов.** Польза видна прямо в вызове `Fighter(...)`, пример до и после легко сравнить, а существующее позиционное создание можно сохранить.

**Для фичи, которая задаёт характер языка, — `when` со значением.** Есть реальная демонстрация с ошибкой, работающие суммы и проверка полноты. Одна короткая функция `area` даст сквозной критерий: прямоугольник 2 × 4 возвращает 8, а новый вариант фигуры требует ещё одной ветки.

**Для более крупного изменения — массив, который несёт длину.** Он упростит сразу несколько настоящих алгоритмов и даст основу для проверяемой индексации и обхода коллекций.
