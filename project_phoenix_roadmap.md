### 1. Идентичность объявления от исходника до C

```bred
fun f() {
    for (i in 0 to 2) { var i: Int = 77 }
}
```

**Сбой.** В текущем TAC сравнение читает `local_i_19`, а `ADD_i32` меняет `local_i_21`. Внешний счётчик остаётся нулём. В сравнительном запуске exe на `master` тело выполнялось один раз, на `phoenix` процесс остановил таймаут 3 с. В новом нативном запуске вариант с явным подсчётом итераций также остановлен по таймауту 2 с. Правильный результат — две итерации. Замена `var` на `val` даёт ошибку изменения неизменяемой переменной на синтетическом шаге. Парсер берёт список инструкций пользовательского блока и добавляет инкремент прямо в ту же область. Служебное имя границы с префиксом `$` решило прежний захват `_right_borderi`, но доходит до C. [ForParser](parser/src/main/kotlin/org/nnezh/bred/ast/ForParser.kt) · [Сравнение веток](PROJECT-PHOENIX.md#asd-2)

**Другие проявления.** Для `type Flag = Off | On` функция `fun f(Off: Int): Int { return Off }` получает в TAC `CALL Off:Flag` и возвращает `Flag`. Analyzer выбрал параметр, lowering снова ищет конструктор по лексеме. У `fun f() { val a: Int = 1 val a: Int[1] = [2] }` проигнорированный отказ `declareVariable` оставляет массив без ID, затем `LLTACGenerator.visit` падает с NPE. Глобальное `val b: Box = Box(b.n)` допускает преждевременное чтение собственного поля. Все три случая проверены на этой ветке. Отдельная коллизия возникает при назначении C-имени. Массив `values` и функция `global_values_18` получили общее имя в C, хотя на `master` эта программа вернула 4. [Analyzer](analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt) · [Lowering выражений](tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACExpressionSubgenerator.kt) · [Коллизия имён](PROJECT-PHOENIX.md#backend-5)

**Порядок правок.**

1. Сохранить пользовательское тело `for` отдельным блоком. Условие и шаг привязать к объявлению счётчика цикла, верхнюю границу вычислять один раз. Проверять достижимость внутри исходного тела. Нативный тест считает итерации, имеет таймаут и ожидает 2 для `var` и `val`. Добавить пустой диапазон, вложенный цикл и параметр `_right_borderi`.
2. Сделать регистрацию переменной однократной. Проверить повтор и инициализатор до публикации привязки, провести через одно правило scalar, array, global и параметры. Сохранить действующий запрет самоссылки также для поля и индекса. Один повтор даёт `VARIABLE_REDECLARATION`, одно затенение — одно предупреждение, у повторных параметров доступны обе позиции. Ранее объявленный продукт по-прежнему можно читать.
3. Передавать в lowering один результат подготовки с финальным деревом, контекстом, таблицами и предупреждениями. Таблицы привязаны к экземплярам узлов. Клон дерева или пропущенные metadata должны обнаруживаться на входе. В `root`, TAC API и TAC CLI выделить общий проход `collect → resolve → collect → instantiate → collect → resolve → analyze`. Загрузку stdlib и набор extern задаёт вызывающая сторона. Переносить исходные позиции через клонирование и специализацию, у синтетического шага хранить ссылку на исходный `for`.
4. Читать выбранную привязку напрямую, включая параметр `Off`. На границе C назначать переносимые имена каждому символу, зарезервировать имена runtime и учитывать функции, глобалы, поля и локальные значения в соответствующих пространствах имён C. Один и тот же выбор должен применяться к объявлению и всем использованиям. Приёмка — обычный `Off` без затенения создаёт вариант, одноимённый параметр возвращает переданный `Int`, пользовательский `checked_add_i32` и runtime-сложение работают в одном exe. Сохранить зелёные проверки `var3`, полей и глобальных массивов. ### 2. Представление и время жизни данных

```bred
fun tokens(): Array<Int> {
    val a: Int[1] = [7]
    return a
}
```

**Корень.** Тип `Array<Int>` сообщает тип элемента. Для генерации ещё нужны владелец хранения, время жизни и длина. В полученном C функция `tokens` объявляет локальный `int local_a_19[1]` и возвращает его адрес. Время жизни заканчивается при выходе. Другая программа, `fun f(a: Int[]): Int { val b: Array<Int> = a return b[0] }`, сохраняет верный `ASSIGN` в TAC, но в C имя `local_b_20` используется без объявления. Сканер локальных массивов распознаёт только `ALLOC`. [Разбор сгенерированного C](docs/GENERATED_C_REVIEW.md) · [Представление параметров](docs/type_system.md)

| Что ломается сейчас | Что сделать и как принять |
|---|---|
| Глобальный `val limit: Int = 7` даёт `RET global_limit_18:Int` без определения. Глобальный `val nums: Int[1] = [-1]` доходит до исключения lowering. Вызов пользовательской `make()` в глобальном initializer отклоняется ещё при анализе | Начать с инструкции объявления глобального скаляра и набора допустимых констант. Общее хранение видно двум функциям. До emission проверять форму initializer, отрицательные константы обрабатывать с правилами диапазона. В ожиданиях `complexShock` разрешить явные объявления в преамбуле, сохранив запрет обычного `ASSIGN` на уровне файла |
| Статический массив, ссылка-параметр и локальный псевдоним имеют разное C-хранение. `return []` проверенно даёт NPE в analyzer, а `Int[0] = []` имеет контекст элемента | Различать эти виды хранения. Пустой initializer типизировать по объявлению, в недопустимой позиции выдавать ошибку. Первой мерой для времени жизни отклонять возврат локального массива, в том числе через псевдоним. Отдельно проверить возврат аргумента и глобала. Для границ и чтения до первой записи выбрать правило языка, для параметров определить источник длины |
| `type S = A_B(c: Int) \| A(B_c: Long)` выдаёт два поля `A_B_c` уже в TAC. `when`, создание суммы и чтение payload отдельно восстанавливают расположение полей | Хранить соответствие «вариант, поле → место хранения» один раз. Analyzer передаёт выбранный образец и привязки ветви. TAC для конструктора и `LOAD_FIELD` использует ту же таблицу. Проверить оба варианта с разными значениями и совпадающими частями имён |
| Цепочка `A → B → C → D` дошла до C, где `A` напечатана раньше полного определения `B`. Цикл `type Loop(next: Loop)` тоже дошёл до C | Сначала зарегистрировать имена, затем рассчитать зависимости полей по значению. Ациклические определения вывести в топологическом порядке, цикл диагностировать в Bred с путём. Проверить оба порядка объявлений. Для пустого продукта и массива длины 0 выбрать представление, которое принимает MSVC, либо раннее ограничение. Проверить создание и передачу пустого значения |

Первый самостоятельный результат здесь — два чтения одного глобального скаляра с ожидаемым значением 7 в exe. Затем можно отдельно ввести проверку выхода локального хранения и общий расчёт размещения полей. Результаты для неинициализированного элемента и чтения по недействительному адресу нельзя фиксировать снимком запуска. fun id<T>(x: T): T { return x }

### 4. Структура TAC и порядок эффектов

```bred
fun g() {}
fun f() { return g() }
```

**Сбой.** Успешный анализ даёт `CALL var1:Unit` и `RET var1:Unit`. В проверенном C появилась локальная `void var1;`. Для `return when (n) { 0 -> { println("0") } else -> { println("1") } }` в функции с результатом `Unit` lowering бросает исключение. Другая сторона той же границы — полный statement-`when` по сумме с `return` в каждой ветви даёт `EXPLICIT_RETURN_IS_EXPECTED`. Полнота образцов уже известна analyzer, но сведения о завершении ветвей проверяются отдельно. [Контракт эффектов](docs/AST_TAC_CONTRACT.md) · [Анализ потока](docs/ANALYZER_REVIEW.md)

**Как исправлять.**

1. Выделить у lowering два результата — вычислен операнд или выполнен эффект. Для `return g()` нужны один вызов без получателя и пустой `RET`. Для `Unit-when` использовать понижение ветвей с эффектами либо выдать раннюю ошибку неподдержанной позиции. В проверке возвратов учитывать полный `when` и достижимость синтетического хвоста. Удаление `return` из одной достижимой ветви снова должно давать ошибку. Реализация `when`, возвращающего произвольное значение, — отдельное расширение языка.
2. Собрать вычисленные аргументы в упорядоченный список в самом `CALL`. При переходе оставить адаптер для клиентов плоского TAC и проверять, что старому вызову предшествует нужное число `PARAM`. Сегодня `ASSIGN x 1` перед `CALL g` с одним аргументом может стать «параметром». Для `f(g(1), h(2))` проверить порядок и однократность эффектов. Сохранить вычисление обоих операндов `&&` и `||`. В TAC для `false && (readInt() > 0)` вызов чтения предшествует `AND`. [Архитектура TAC](docs/TAC_ARCHITECTURE.md)
3. Описать чтение значения у `PARAM`, изменение памяти у `STORE` и ссылку на метку своей функции у `JMP`. ### 5. Строки и операции над составными значениями

```bred
fun main(): Int {
    val src: String = "hello"
    val dst: String = src
    println(dst)
    return 0
}
```

**Тихая порча результата.** При запуске через TAC → C → MSVC программа напечатала `local_src_19` и вернула 0. Номер зависит от окружения. На `master` ревизия зафиксировала вывод `src`. В обеих ветках backend превращает правую часть `ASSIGN` в текст, затем заключает этот текст в кавычки для любого назначения типа `String`. В действующем runtime строка уже содержит указатель и длину, её значение можно скопировать присваиванием структуры. [Генерация ASSIGN](c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt) · [Проверка обеих веток](PROJECT-PHOENIX.md#backend-2)

**Исправлять по одной операции.**

1. Различить `Operand.StringConst` и `Operand.Variable` до рендеринга. Литерал создать один раз, для готового значения скопировать структуру. Исполняемая проверка для литерала, параметра, переменной и повторного присваивания должна получать `hello`.
2. Определить байтовое представление литерала в одном месте для локальных и глобальных строк. В прежнем нативном тесте глобальное `"é" + "!"` дало байты `C3 21` при ожидаемых `C3 A9 21`. Kotlin считает кодовые единицы, runtime копирует байты. Для `"a\0b"` проверить сохранение трёх байтов и вывод с учётом длины, включая нулевой байт. Выбор кодировки сделать независимым от кодовой страницы компилятора.
3. Для `a == b` при типе `String` задать сравнение длин и байтов и проверить реальный экспорт runtime. Для продуктов и сумм определить допустимые сравнения или диагностировать неподдержанный оператор до C. Обычный `==` над C-структурами отвергает компилятор. Исторический `stringproposal.txt` описывает желаемый helper, наличие реализации надо проверять в текущем runtime.
4. Для многократного `s = s + "x"` измерить объём выделений и границу пула 16 МиБ. Отдельно измерить стек больших локальных массивов из группы 2. Пока известна ёмкость пула и удержание промежуточных значений. Число итераций до отказа и стоимость оптимизаций требуют замера. ### 6. Числовые границы

```bred
fun minimum(): Int { return -2147483648 }
```

**Сбой.** Лексер отдельно читает знак и цифры. Ветка проверяет `2147483648` через `toIntOrNull()` прежде, чем станет известно о минусе. Нативный тест минимума останавливается ещё при компиляции Bred. На `master` чрезмерная величина могла тихо сузиться, в том числе в размере массива. При этом обычный новый путь сложения корректно ловит переполнение в runtime. [Лексер](lexer/src/main/kotlin/org/nnezh/lexer/Lexer.kt) · [Исполняемые тесты](src/test/kotlin/org/nnezh/root/IntegerExecutionTest.kt)

**Границы правки.** Сохранить цифры или широкую величину до определения знака и требуемого типа. Проверить минимум, максимум, соседние значения, положительное переполнение, суффикс `L` и `Int[4294967296]`. Затем установить единое правило для `ADD_i32` и старого `ADD` с `Int` на прямом входе backend. Принимать старую форму с той же проверкой либо отклонять её предметно. Сохранить позицию оператора и код 1 при переполнении.

Для `-`, `*`, деления на ноль и минимума, делённого на −1, отдельно выбрать поведение и проверить границы. Для смешанного сравнения `1 < 2L` текущий путь до C работает, смешанная арифметика подчиняется более строгому правилу. Закрепить оба случая. В `doubleToString(100000000000000000000.0)` есть отдельный риск преобразования конечного `Double` в `long long` вне диапазона. Проверить оба знака, обычные шесть знаков после запятой, NaN и ±Inf. Это изменение форматирования можно поставить независимо от лексера. [Числовые контракты](PROJECT-PHOENIX.md#backend-17) · [Семантические правила](docs/semantic_analysis_draft.md)

### 9. Конец ввода в runtime

**Воспроизведено в exe.** Для `fun main(): Int { return readInt() }` процесс пришлось завершить через 2 с как при пустом закрытом stdin, так и при подаче `abc` перед EOF без перевода строки. После неуспешного `scanf_s` цикл восстановления ждёт исключительно `'\n'`. Каждый следующий `getchar()` снова возвращает EOF. Корневой CLI теперь ждёт exe, поэтому зависает и вызывающий скрипт.

Минимальная совместимая правка — завершать восстановление и по EOF, сохранить действующий результат 0 при ошибочном токене и записать это правило для пустого ввода. Приёмка — два указанных процесса завершаются в таймауте, корректное число по-прежнему читается, после некорректной строки с переводом строки доступно следующее число. Правку можно внести независимо от всей ветки компилятора. [readInt](runtime.c) · [Исходное наблюдение](PROJECT-PHOENIX.md#backend-4)
