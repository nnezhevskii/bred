# PROJECT PHOENIX

Ревизия от **14 ноября 2026 года**. Сравнены локальные `master` (`e965c6e`, общий предок) и `phoenix` (`26b9618`). Ветка опережает `master` на 8 коммитов, в `git diff master...HEAD` изменены 100 файлов. Предыдущая ревизия заканчивалась на `3e03c3f`. В следующих четырёх коммитах изменились регистрация глобальных массивов и способ проверки TAC.

| Что изменилось с `master` | Что показала проверка |
|---|---|
| Analyzer передаёт в TAC идентификаторы объявлений | Параметр `var3` сохраняет своё значение. В нативном тесте запись во внутренний `Counter` даёт `42`, чтение внешнего даёт `7`. Глобальный массив и его чтение теперь имеют один `GlobalVar`. [3АК 1–2](#tac-1) · [АСД 4](#asd-4) |
| Сложение двух `Int` проверяет переполнение | Для `2147483647 + 1` программа сообщает позицию плюса и завершает работу с кодом 1. Лексер также отклоняет слишком большие литералы, но вместе с ними отклоняет допустимый `-2147483648`. [Бекенд 17](#backend-17) · [АСД 1](#asd-1) |
| Вызов с отброшенным результатом сохраняет тип | Обычный вызов `g(): Int` даёт `CALL g:Int` без получателя. Отброшенный конструктор продукта по-прежнему превращается в ошибочный вызов C. [3АК 5](#tac-5) |
| Тесты сравнивают типизированные инструкции | Проверяются все 22 программы из ресурсов, в том числе 14 ранее исключённых. Тест видит точное значение строки, тип операнда и цель перехода. [3АК 13](#tac-13) · [3АК 14](#tac-14) |
| Корневой CLI после сборки запускает exe | Программа наследует stdin/stdout, CLI ждёт её и передаёт код выхода. Запуск с `return 7` вернул 7. Явный `keep-c=false` по-прежнему оставил C-файл. [Бекенд 12](#backend-12) · [Бекенд 19](#backend-19) |

**Регрессии, проверенные на одинаковом исходнике в обеих ветках**

1. **Зависание при затенении счётчика `for`.** На `master` цикл ошибочно завершался после первой итерации. На `phoenix` условие читает внешний счётчик, а инкремент меняет внутренний. Через 3 секунды тест остановил процесс. [АСД 2](#asd-2)
2. **Коллизии новых имён в C.** Функция `global_values_18` и массив `values` собирались на `master`, программа возвращала 4. На `phoenix` MSVC отвергает их как два объявления одного имени. Отдельно перестал собираться ранее принимавшийся `main(size: Int)`. [Бекенд 5](#backend-5) · [Бекенд 6](#backend-6)
3. **Ошибки при регистрации переменных.** Анализатор теперь принимает чтение поля глобального значения в его собственном инициализаторе. Повтор локального имени у массива обе версии пропускают, но теперь генератор TAC падает с `NullPointerException`. [АСД 4](#asd-4)

**Полный прогон.** Обе версии проверены на JDK 25 с доступным MSVC командой `.\gradlew.bat test --offline --rerun-tasks --continue`. Для `master` использована отдельная копия из `git archive e965c6e`. В таблице указано число успешных тестов из числа выполненных. Пропусков в обоих прогонах 0.

| Версия | lexer | parser | analyzer | tac | c-backend | корень | Всего |
|---|---:|---:|---:|---:|---:|---:|---:|
| `master` | 48/48 | 103/105 | 152/152 | 50/50 | 17/17 | 14/15 | **384/387** |
| `phoenix` | 48/48 | 103/105 | 152/156 | 135/140 | 17/17 | 19/23 | **474/489** |

Три падения на `master` связаны с тестами радара, которые читали изменившееся CLI-демо. В `phoenix` эти проверки закомментированы вместе с семантическим тестом радара. В новом прогоне упали другие тесты. Из 15 падений одно вызвано устаревшим ожиданием имени глобального массива `Long`. По сравнению с предыдущей ревизией один тест analyzer стал зелёным, а этот тест TAC стал красным. [АСД 21](#asd-21) · [3АК 13](#tac-13)

### Задача 1. Сохранить значение Int-литералов и размеров до проверки диапазона

- [ ] **Критичность — P1.** G-78. **Основание — код лексера и отказ публичного компилятора на минимальном Int.**

На `master` значения `2147483648` и `Int[4294967296]` могли измениться при сужении. В `phoenix` лексер проверяет цифры через `toIntOrNull()` до построения дерева. Остался граничный случай:

```bred
fun minimum(): Int { return -2147483648 }
```

Минус разбирается отдельно. На `master` этот пример доходил до TAC как присваивание уже суженного `-2147483648` с последующим `NEG`. Нынешний лексер выдаёт `InvalidNumber` для положительной части `2147483648`, хотя значение выражения помещается в Int. Корневой `IntegerExecutionTest` останавливается на лексере до запуска MSVC.

**Критерий готовности.** Минимальный Int сохраняет значение, положительное переполнение и чрезмерный размер массива дают диагностику, суффикс Long сохраняет диапазон Long. Проверка сложения во время выполнения описана в [бекенде 17](#backend-17).

### Задача 2. Исключить захват имён при разворачивании for

- [ ] **Критичность — P1.** G-95. **Основание — TAC и запуск exe на обеих ветках, два регрессионных теста TAC.**

Для исходного примера с параметром `_right_borderi` TAC теперь передаёт в тело цикла параметр. Верхняя граница хранится отдельно. Открытый дефект касается самого счётчика:

```bred
fun f() {
    for (i in 0 to 2) { var i: Int = 77 }
}
```

На `master` в C был один `i`. Тело присваивало ему 77, инкремент давал 78, цикл завершался после первой итерации. На `phoenix` условие читает внешний `local_i_19`, а инкремент читает и меняет внутренний `local_i_21` (имена из TAC функции `f`). Внешний счётчик остаётся равен нулю. Для нативной проверки то же тело помещено в `fun main(): Int` с `return 0` после цикла. На `master` процесс вернул 0, на `phoenix` его остановил таймаут 3 с. Замена `var` на `val` приводит к `VARIABLE_CHANGING_IMMUTABLE` на синтетическом присваивании.

**Критерий готовности.** Обе версии выполняют две итерации. Сравнение и инкремент используют одну привязку счётчика, а пользовательская переменная в теле сохраняет собственную привязку.

### Задача 4. Регистрировать переменную один раз, после проверки инициализатора

- [ ] **Критичность — P1.** **Основание — запуск TACCompilerImpl, тесты SemanticAnalyzer и чтение declareVariable.**

```bred
fun f() {
    val a: Int = 1
    val a: Int[1] = [2]
}
```

На `master` analyzer принимал такой повтор, а в C появлялись скаляр и массив с одним именем. Теперь `declareVariable` возвращает `Left`, ветка массива отбрасывает его и сообщает об успехе. Для второго объявления отсутствует символ. Вызов `TACCompilerImpl.compile` завершается `NullPointerException` в `LLTACGenerator.kt:261`. Два объявления массива в том же блоке также проходят анализ.

**Исправлено для глобальных массивов.** На `3e03c3f` первая регистрация создавала `LocalVar`. Теперь она создаёт `GlobalVar`, и тест analyzer подтверждает идентичность символа у объявления и чтения. Две проверки в `TACInstructionSequenceTest` связывают `LOAD` с соответствующим глобальным массивом с инициализатором и без него. Вторая регистрация глобальной переменной по-прежнему расходует ID и отбрасывает ошибку повтора. Локальное скалярное объявление по-прежнему дважды проверяет затенение. [АСД 19](#asd-19)

**Новая регрессия для глобальных продуктов.** На обе версии `TACCompilerImpl` передан один исходник.

```bred
type Box(n: Int)
val b: Box = Box(b.n)
fun f() {}
```

На `master` анализ завершился с `UNKNOWN_FIELD`. На `phoenix` имя `b` уже видно в собственном инициализаторе. Чтение переменной и индекса проверяет `isInitializing`, а `fieldAccessTarget` сразу ищет корень в области видимости. Анализ принимает чтение `b.n` до создания `b`. Полученный TAC содержит определение `Box` и функцию `f`. Отсутствие определения глобального скаляра в TAC отслеживается отдельно. [SemanticAnalyzer](analyzer/src/main/java/org/nnezh/SemanticAnalyzer.kt) · [3АК 6](#tac-6)

**Критерий готовности.** Каждое объявление регистрируется один раз. Повторы scalar/array и array/array дают `VARIABLE_REDECLARATION` на втором объявлении. Самоссылка через поле получает семантическую ошибку, чтение поля ранее объявленного продукта проходит анализ. Глобальный массив и обращения к нему сохраняют один `GlobalVar`.

[Подробности и результаты исходной проверки](docs/ANALYZER_REVIEW.md)

### Задача 6. Не выпускать наружу адрес локального массива

- [ ] **Критичность — P1.** **Основание — Проверен сгенерированный C; разыменование после возврата не выполнялось.**

### Задача 12. Валидировать typeclass и instance независимо от использования

- [ ] **Критичность — P2.** Связанные задачи — G-47. **Основание — Воспроизведено.**

**Пример кода.**

### Задача 5. Отображать Bred-идентификаторы в допустимые уникальные C-имена

- [ ] **Критичность — P1.** **Основание — сгенерированный C и отдельная сборка с MSVC.**

12 ноября параметр `switch` попадал в C как ключевое слово. Теперь параметры получают префикс и номер. Для границы `for` генератор, однако, выдаёт имя вида `local_$_right_borderi_26`. Знак `$` в таком идентификаторе требует поддержки расширения C. Тест проверяет текст реального вывода.

```bred
fun checked_add_i32(a: Int, b: Int): Int { return a - b }
```

Это допустимое имя Bred совпало с новым helper из `runtime.c`. Нативная проверка вызывает пользовательскую функцию и обычное сложение. MSVC сообщает C2084 о повторном определении и C2197 о числе аргументов. Подтверждение получено при запуске новых тестов после исходного анализа диффа.

**Новая коллизия между пользовательскими объявлениями.** В Bred имена `values` и `global_values_18` различны.

```bred
val values: Int[1] = [4]
fun global_values_18(): Int { return values[0] }
fun main(): Int { return global_values_18() }
```

Тот же исходник через корневой компилятор со stdlib и MSVC на `master` вернул 4. На `phoenix` и глобальный массив, и функция получили C-имя `global_values_18`. MSVC выдал C2365 при объявлении функции и C2063 на вызове. Номер 18 соответствует текущему порядку выдачи символов. Причина воспроизводится и в TAC API внутри функции, где имя локальной переменной вида `local_x_20` может скрыть одноимённую пользовательскую функцию. `SymbolId.toString()` задаёт имя переменной в C, тогда как `mangleFunctionName` возвращает исходное имя функции. [SymbolId](common/src/main/kotlin/org/nnezh/bred/common/SymbolId.kt) · [LLTACGenerator](tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACGenerator.kt)

**Критерий готовности.** Единое правило именования учитывает функции, переменные, временные значения и символы runtime. Программа с глобальным массивом возвращает 4, программа с `checked_add_i32` выводит 7 и 11, идентификаторы границ цикла допустимы в целевом диалекте C.

### Задача 12. Передавать статус сборки отдельно от текстовых сообщений

- [ ] **Критичность — P1.** G-77. **Основание — код Main и CExecutableBuilder, запуск корневого CLI в отдельном процессе.**

На `master` поиск слов `error` и `failed` в сообщениях путал имя каталога с отказом сборки. Теперь CLI извлекает путь из последней строки builder по префиксу `Generated executable: `, запускает exe с унаследованной консолью, ждёт его и возвращает код программы. **Критерий готовности.** Builder передаёт статус и путь отдельными значениями. Отсутствующий runtime даёт ошибку сборки, успешный путь через каталог `errors` передаёт код программы, изменение текста лога сохраняет это поведение.

### Задача 17. Зафиксировать числовой контракт сгенерированной C-арифметики

[Lowering выражений](tac/src/main/kotlin/org/nnezh/ICGenerator/LLTACExpressionSubgenerator.kt) · [CTranspile](c-backend/src/main/kotlin/org/nnezh/compiler/CTranspile.kt)

Для остальных целочисленных операций определить поведение на границах, включая вычитание, умножение, деление на ноль и деление минимума на −1.

```powershell
.\gradlew.bat run --args="examples/3ac.bred build/out/demo.exe false"
.\gradlew.bat run --args="examples/3ac.bred build/out/demo.exe true"
```

**Мотивация.** Main разбирает третий аргумент с умолчанием `true`, затем безусловно передаёт builder значение `true`. Тест с явным `false` получил ожидаемый код программы 7 и обнаружил сохранённый `exit.c` во временном каталоге.

**Критерий готовности.** C сохраняется только по выбранной опции; удаление ограничено собственным промежуточным файлом.

### Задача 20. Проверять результат программы через реальный C-компилятор

- [ ] **Критичность — P2.** G-84, G-91. **Основание — три выполненных теста ProductFieldExecutionTest с MSVC и сравнение примеров.**

Проверки теперь проходят путь Bred → C → exe и сравнивают stdout. Присваивание полю затенённого объекта сохраняет внешний объект, запись вложенного поля сохраняет соседнее поле, одинаковые имена привязок в разных ветвях `when` дают payload выбранного варианта.

Дефект демонстрационной площади относится к примеру фигур от 12 ноября. В текущем CLI-примере читается элемент глобального массива. Покрытие компиляции радара в C остаётся открытым. [АСД 21](#asd-21)

**Критерий готовности.** Дополнить нативные проверки строковым присваиванием и компоновкой extern-функций. Запрещённые вложенные массивы должны давать диагностику на публичном пути. Состояние арифметических проверок приведено в [бекенде 17](#backend-17).

### Задача 21. Централизовать целевое представление типов, литералов и runtime-операций

- [ ] **Критичность — P3.** **Основание — Архитектурная задача.**

**Описание.** Разделить Bred-тип и C-тип параметра/локального/поля/результата; рендерить литерал после определения его вида. Для пустого списка аргументов учитывать выбранный C-диалект.

**Пример кода.**

```text
// Сейчас две похожие функции выбирают C-типы:
// typeToStringInInitialization(type)
// typeToStringInArguments(type)
// Для C до C23 прототип void f(void) выражает ноль параметров.
```

**Мотивация.** Повторные ветки и трактовка любого resolved named type как продукта скрывают требования представления и runtime.

**Критерий готовности.** Правило каждого поддержанного типа находится в одном владельце; C-литералы печатает backend, сигнатуры соответствуют целевому режиму.

[Подробности и результаты исходной проверки](docs/C_BACKEND_ARCHITECTURE.md)

### Задача 22. Локализовать состояние transpiler и улучшить диагностику C

- [ ] **Критичность — P3.** **Основание — Архитектурный риск; конкурентный сбой не воспроизводился.**

**Описание.** Сделать sumDefinitions и состояние текущей функции локальными для одного compile. Отличать ошибку входного IR от внутреннего сбоя и связывать строки C с TAC/исходником.

**Пример кода.**

```kotlin
// Kotlin, два независимых входа одним объектом:
val backend = CTranspile()
backend.compile(firstProgram)
backend.compile(secondProgram)
// Отдельно проверить перекрывающиеся вызовы,
// если публичный API допускает такую работу.
```

**Мотивация.** Последовательный reset протестирован, но изменяемые поля общего объекта мешают безопасному совместному использованию. catch(Throwable) может скрыть внутреннюю причину.

**Критерий готовности.** Повторное использование определено; при заявленной конкурентности нет общих изменяемых данных. Ошибка содержит стадию и происхождение.

[Подробности и результаты исходной проверки](docs/C_BACKEND_ARCHITECTURE.md)
