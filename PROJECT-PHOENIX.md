### Задача 1. Сохранить значение Int-литералов и размеров до проверки диапазона

- [ ] **Критичность — P1.** Связанные задачи — G-78. **Основание — Воспроизведено.**

**Описание.** Заменить безусловное сужение Long → Int проверкой диапазона. Сейчас значение и размер могут тихо измениться ещё при построении дерева.

**Пример кода.**

```bred
fun f(): Int { return 2147483648 }
fun g() { val a: Int[4294967296] }
```

**Мотивация.** После потери исходного числа все следующие стадии проверяют уже другую программу.

**Критерий готовности.** Число вне Int даёт диагностику, огромный размер не превращается в 0. Проверены границы Int, Long-суффикс и отрицательный минимум.

**Критерий готовности.** Есть ограниченный по времени тест нагрузки и ясная диагностика. Оптимизация выделений назначается по замеру.

[Подробности и результаты исходной проверки](docs/GENERATED_C_REVIEW.md)

<a id="backend-17"></a>

### Задача 17. Зафиксировать числовой контракт сгенерированной C-арифметики

- [ ] **Критичность — P2.** **Основание — Риск по рендеру операций.**

**Описание.** Определить поведение переполнения, деления на ноль и операции над минимальным знаковым значением. Не полагаться на /Od как на семантическую гарантию.

**Пример кода.**

```bred
fun overflow(x: Int): Int { return x + 1 }
fun divide(x: Int, y: Int): Int { return x / y }
// Контроли: x = Int.MAX_VALUE и y = 0.
```

**Мотивация.** Обычные знаковые C-операторы не задают безопасное поведение всех входов.

**Критерий готовности.** Выбранное поведение описано, для границ есть проверки. Нативные опасные случаи выполняются только под контролем теста.

[Подробности и результаты исходной проверки](docs/GENERATED_C_REVIEW.md)

### Задача 18. Обработать большие конечные Double в форматировании

- [ ] **Критичность — P2.** Связанные задачи — G-90. **Основание — Риск по runtime.**

**Описание.** Проверить диапазон перед масштабированием и преобразованием к long long либо использовать форматирование с заданным контрактом.

**Пример кода.**

```bred
fun main() {
    println(doubleToString(100000000000000000000.0))
}
```

**Мотивация.** Текущее масштабирование и приведение могут выйти за представимый диапазон целой части даже для конечного Double.

**Критерий готовности.** Проверены большие значения обоих знаков, NaN/Inf и обычные дроби; нет неоговорённого преобразования вне диапазона.

### Задача 20. Проверять результат программы через реальный C-компилятор

- [ ] **Критичность — P2.** Связанные задачи — G-84, G-91. **Основание — Проблема демо подтверждена запуском; потребность в тестах подтверждена ревизией.**

**Описание.** Дополнить строковые проверки compile-only, link и stdout-сценариями. Проверить обработку запрещённых вложенных массивов на публичном пути. Исправить демонстрационную площадь.

**Пример кода.**

```bred
fun square(a: Double): Double {
    var value: Double = a * a
    return 0.0 // В демонстрации теряется вычисленный value.
}
```

**Мотивация.** 17 зелёных строковых тестов не ловят неверный stdout, отсутствие C-типа или символа runtime. Текущий пример фигур возвращает константу.

**Критерий готовности.** Для одного значения есть проверка 8 или 16; отдельные тесты ловят строки, типы и компоновку. Вложенные массивы получают понятную диагностику действующего ограничения.

### Задача 21. Централизовать целевое представление типов, литералов и runtime-операций

- [ ] **Критичность — P3.** **Основание — Архитектурная задача.**

**Описание.** Разделить Bred-тип и C-тип параметра/локального/поля/результата; рендерить литерал после определения его вида. Для пустого списка аргументов учитывать выбранный C-диалект.

**Пример кода.**

```text
// Сейчас две похожие функции выбирают C-типы:
// typeToStringInInitialization(type)
// typeToStringInArguments(type)
// Для C до C23 прототип void f(void) выражает ноль параметров.
```

**Мотивация.** Повторные ветки и трактовка любого resolved named type как продукта скрывают требования представления и runtime.

**Критерий готовности.** Правило каждого поддержанного типа находится в одном владельце; C-литералы печатает backend, сигнатуры соответствуют целевому режиму.

### Задача 22. Локализовать состояние transpiler и улучшить диагностику C

- [ ] **Критичность — P3.** **Основание — Архитектурный риск; конкурентный сбой не воспроизводился.**

**Описание.** Сделать sumDefinitions и состояние текущей функции локальными для одного compile. Отличать ошибку входного IR от внутреннего сбоя и связывать строки C с TAC/исходником.

**Пример кода.**

```kotlin
// Kotlin, два независимых входа одним объектом:
val backend = CTranspile()
backend.compile(firstProgram)
backend.compile(secondProgram)
// Отдельно проверить перекрывающиеся вызовы,
// если публичный API допускает такую работу.
```

**Мотивация.** Последовательный reset протестирован, но изменяемые поля общего объекта мешают безопасному совместному использованию. catch(Throwable) может скрыть внутреннюю причину.

**Критерий готовности.** Повторное использование определено; при заявленной конкурентности нет общих изменяемых данных. Ошибка содержит стадию и происхождение.
